1. 使用する教材とリポジトリの分離

教材の配布と受講者環境

  • 受講者への配布：参加者には App の目次 のみを配布します。CLI 独立コースや Mona Mayhem は補講用の参考資料です。本編の途中で受講者を移動させてはなりません。
  • 演習用リポジトリ：演習は、教材用テンプレートから各自が作成したTailspin Toysのコピー環境で行います。
  • 教材リポジトリの保護：受講者が本教材リポジトリ（dev-days-jp）内で直接アプリ実装の演習を行わないよう徹底してください。

参照元リポジトリの取り扱い

参照元は github/dev-days（開催・運営資料）および github-samples/copilot-workshops（App シナリオ）です。参照コミットと対象ファイルは content/ja/sources.json に記録されています。参照元への push や Pull Request など、いかなる変更送信も一切行いません。

掲載画像と検証範囲

Appは最新版で実施します。検証日・使用環境・章ごとの結果・未確認事項・掲載画像の状況は、検証記録にまとめています。

各章では操作対象・項目名・判断する内容を説明しています。講師は開催前に、UI確認表と検証記録を参照し、当日の最新版で操作できることを確認してください。画像ごとの撮影条件は content/ja/sources.json の ui_captures に記録しています。

操作と判断を結び付ける教え方

この研修では、受講者が「自分でも同じボタンを押せた」ことに加えて、「何を確かめてから次へ進んだか」を説明できることを目標にします。Tailspin Toysの利用者がゲームを見つけやすくなる、という共通の目的を導入で共有し、星評価・絞り込み・検索がその目的のどの部分を受け持つかを問いかけてください。

各演習では、操作前に予想を立て、実行後に結果と比べる時間を設けます。たとえばフィルターの複数選択を試す前に、ORとANDでは表示件数がどう変わるかを受講者に説明してもらいます。予想と違った場合は、その場で追加プロンプトを渡す前に、要件・テストデータ・実装のどれを調べると切り分けられるかを考えてもらいます。

章 講師が確認したい理解 受講者への問いかけ例
1・2 教材と演習コピー、会話と作業セッションの役割 「今から変更されるリポジトリはどれですか」
3 小さな変更でも差分と動作を確認する理由 「評価0と未評価を同じ表示にしてよいですか」
4 共通の指示と機械的な品質検査の使い分け 「この規約は全体の指示、パス固有の指示、ESLintのどこへ置きますか」
5 実装前に仕様の曖昧さを解消する意味 「StrategyとPuzzleを選ぶと、どのゲームが表示されるはずですか」
6 ツールへの接続とツール実行の成功の違い 「Connectedの表示だけでは、何がまだ分かりませんか」
7 自動化へ委ねる権限と人が確認する根拠 「マージしてよいと判断した根拠を、画面とCIで示せますか」
8 Issueを共有の作業面へ載せる価値と情報の鮮度 「カードを会話へ追加することと、実装開始は同じですか」
9 実行成功とレポートの正確さの違い 「Succeededの結果を、どのGitHub情報と照合しますか」

生成されたコードや文言が講師の実行結果と一致することを採点基準にしません。受講者が要件を満たした証拠を示せるか、既存の機能への影響を説明できるかを確認します。GitHub公式にも、人が変更をレビューしてフィードバックを返す開発フローが示されています。出典：GitHub Copilot Appの開発フロー。

困っている受講者には「答えのプロンプト」をすぐ渡す前に、現在の目的と観察できた結果を言葉にしてもらいます。一方、認証・利用枠・通信など学習内容と直接関係しない停止は講師が切り分け、仕様を考える時間を確保してください。

2. 講師向け資料と公式イベント運営上の注意点

2026年9月13日に、上流のコミット 54ae7ea に含まれる FAQ とコンテンツ案内を確認しました。App の演習コードを変更する更新ではないため、次の案内事項のみを反映しています。

利用可能な公式リソース

  • 日本語の App 講師向け動画 および App スライド が提供されています。実演の準備に活用してください。
  • 上流の 日本語 App ワークショップ は参照用の資料です。本教材では、実機検証済みの操作手順と修正済み演習テンプレートを使用します。

公式イベント運営の厳格な条件

  • 新規申請の受付終了：指定コミットの時点で、公式 Dev Days の新規イベント申請は定員到達により受付・承認を終了しています。本コピー内の旧イベント申請案内ではなく、公式 FAQ で最新状況を確認してください。
  • 登録の一本化：公式 Dev Days として承認済みのイベントは、Luma で Public に設定し、参加登録も Luma に集約します。他の告知サービスを併用する場合も、登録窓口を分散させてはなりません。日程変更なども Luma に反映します。
  • 必須登録項目：登録時には、国、GitHub ユーザー名、職種への回答を必須とします（会社名および連絡への同意は任意です）。
  • 報告義務：参加者には 終了後アンケート を案内し、主催者は飲食費精算の有無にかかわらず 開催報告 を提出する義務があります。

重要 上記は公式イベントとして承認された場合の運営条件です。独立した勉強会を開催しても、公式承認や特典が自動的に付与されるわけではありません。クーポン、物品、飲食精算はイベントごとの個別承認条件に従います。受講者全員への提供を安易に約束せず、公式 FAQ と承認時の案内を確認してください。

以下の配分は本教材独自の運営案であり、実測所要時間ではありません。演習1および演習2の環境準備は、原則として事前準備で済ませておく前提です。原本シナリオの想定（60〜90分）に対し、App の操作支援やレビュー時間を手厚く確保しています。

進行上の注意：CI の待機時間や受講者の環境構築が長引いた場合は、無理に受講者全員の操作を継続させず、後半の演習を「講師デモ」に切り替えて進行してください。その際、受講者本人が実施していない項目は記録に残し、「全員が全演習を完了した」と案内してはなりません。Canvas や Automation を全員にハンズオンさせる場合は、別途追加枠を確保する必要があります。

特に演習8は、ボードを表示するだけでなく、共有・再表示・検索機能の計画と実装までを含みます。10分はその流れを説明するデモ枠です。全員が実装まで行う回では、使用する教材で所要時間を測り、演習と振り返りの枠を追加してください。

4. 開催前のリハーサル項目

講師は開催前に、自身の演習用コピーで次の項目をリハーサルしてください。

  1. 環境とバージョンの記録：演習1〜9を順に通し、App および CLI のバージョン、Node.js バージョン、テンプレートのコミット SHA、OS を記録します。
  2. マージ結果の継承確認：演習3および演習4のマージ結果が、演習5の開始時に正しく引き継がれていることを確認します（CLI コースのように publisher helper が事前に存在すると仮定しないでください）。
  3. 現行 UI 経路の検証：UI 確認表 に沿って、現行 App の操作経路と画面表示を突き合わせます。CLI の緊急対応は、本編とは別の「作業保全リハーサル」として別途確認します。
  4. 利用権限とポリシーの切り分け：App 用および CLI 用の利用ポリシー、残り利用枠（AI Credits など）、ネットワーク接続、必要な GitHub 権限を確認します。UI の変更と、認証や利用枠の枯渇による問題を混同しないようにしてください。
  5. テストケースとデータの確認：星評価の null ケース、フィルターの複合条件・解除・該当なし表示を確認します。通常データ（seed）に存在しない条件は検証用データでテストし、実際の画面操作による結果と明確に区別します。
  6. MCP 実行環境の切り分け：MCP 用の Chrome と E2E 用の Chromium を明確に区別します。MCP 接続失敗時はプロセス状態、App の MCP 設定、セッション再起動を確認してください。手動ブラウザー検証へ切り替えた場合は、MCP 体験を「未実施」とします。
  7. テンプレートの版確認：使用する版はv2026.10.05です。Use this templateはタグではなく既定ブランチを複製するため、開催前に既定ブランチとタグの内容を照合してください。演習済みの検証リポジトリを開始用として配布しないよう注意してください。
  8. 依存性監査の確認：配布元WORKSHOP.mdの10月2日の記録では、依存更新後のクリーンインストールと監査0件が記録されています。これは当時の結果です。開催前は取得した版に対する監査と機能検査を実施し、その時点の結果を判断材料にします。
  9. 終了時の後始末：開発サーバー、演習用 Codespace、不要な定期実行を停止します（作成した PR や未保存の作業ツリーを誤って削除しないようにしてください）。

5. 当日の操作支援と緊急対応ルール

受講者が操作に詰まった場合は、次の原則に従って支援します。

  1. 現状の正確な把握：現在の章、操作の目的、現在の画面表示を確認し、UI 確認表 と照合して差分を記録します。画面上の位置だけで探さず、機能名、対象リポジトリ、セッションの状態を照合してください。
  2. 推測による案内の禁止：講師が実際に検証済みの現行操作経路のみを案内します。見つからない機能に対して、推測で操作を指示してはなりません。
  3. デモ・ペア操作への切り替え：受講者環境で操作が再現できない場合は、同じ操作を講師の実機デモまたはペア操作で示します。受講者が画面を見ただけの項目は「デモ確認」と記録し、受講者本人の実施とは区別してください。
  4. CLI 緊急対応の限定的適用：受講者の作業を保全し、実装を前へ進める必要がある場合に限り、講師専用 CLI 手順 を使用します。時間が経過したという理由だけで安易に CLI へ切り替えてはなりません。また、CLI で実装を完了させても、App の操作体験は「未完了」として記録します。

「機能体験」の厳格な判定基準

  • 環境、権限、利用枠の問題は、UI の仕様変更とは明確に切り分けて記録します。
  • 講師環境でも機能を確認できない章は延期とし、無理に実施可能と案内してはなりません。
  • 代用と体験の峻別：通常の PR 作成、通常の Markdown 文書、単発の要約プロンプト実行を、それぞれ Agent Merge、Canvas、Automation の「実施」に数えてはなりません。

6. 検証記録の更新

当日の結果に基づき、章別検証表 の記録を実測結果と証拠によって更新します。過去の CLI 専用シナリオで CI が成功した実績を、App シナリオの完走へ読み替えてはなりません。

リハーサルでは講師が追加説明した箇所も記録し、次の改訂では、手順が足りなかったのか、判断の理由が伝わらなかったのかを分けて改善してください。教材だけで進められた範囲と、補足して進められた範囲を区別すると、受講者がつまずく箇所を見つけやすくなります。
