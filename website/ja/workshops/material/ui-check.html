App の UI が教材と異なるとき

講師・運営向けの補助資料です。

演習ではGitHub Copilot Appの最新版を使用してください。このページでは、教材と画面が異なるときに操作の入口を探し、演習の目的に沿って案内する方法をまとめています。

検証環境、実走結果、未確認の範囲は検証状況を参照してください。講師は最新版の画面を確かめ、操作の入口と、その場で受講者が判断する内容を案内します。

1. 受講者が操作に迷ったとき

画像の位置だけを頼りにせず、操作対象と目的から確認します。ボタンが見つからないときは、表示条件やセッションの状態も調べてください。

  1. 対象を確認する。リポジトリ、Issue、セッション、変更ファイル、PRのどれを操作する場面かを本文で確かめます。現在選んでいるリポジトリやセッションが違うと、必要な操作が表示されない場合があります。
  2. 目的を確認する。「セッションを開始する」「変更をレビューする」「PRを作る」など、何をしたいかを受講者と確認します。
  3. 講師と入口を探す。サイドバー、対象付近のボタン、メニューを確認します。対象のコンテキストメニューも候補ですが、目的の項目があるかは実際の表示で判断してください。
  4. 実行前に照合する。項目名と作用対象を読み、操作後に何が変わるかを確認します。マージ、削除、自動化など、状態を変える操作を探すために試し押ししないでください。
  5. 見つからなければ案内方法を切り替える。講師の現行画面でのデモ、またはペア操作で確認します。CLIで作業を進めた場合も、Appで未確認の操作は記録に残してください。

2. 操作の入口と判断すること

次の表を使って操作の入口を探してください。最新版で表記や配置が異なる場合も、右欄の確認点を使って演習の目的を確かめます。

操作 操作の入口・進め方 学習上の確認点
演習コピーを作る GitHub WebのUse this template → Create a new repository。コピー後に課題8件の自動生成を確認する 取得先と作成先を確かめ、自分の演習コピーを操作する
リポジトリを接続する Add GitHub repositoryで演習コピーを追加 教材のリポジトリと、コードを変更する演習コピーを区別する
初回の構成を承認する Review repository content → Repository trust → Accept for new sessions セットアップや拡張の内容を読んで承認する。MCPの信頼確認とは別の操作
Issueを探す Projectsで演習用プロジェクトを選び、Issuesフィルターを選択。必要に応じてOpen・割り当てなどの表示条件を見直す Assigned to meが空でもIssueがないとは限らない。表示条件とGitHubの一覧を照合する
PRを探す サイドバーのPull requests 変更したリポジトリとPRの向き先が一致するかを確認する
会話を始める サイドバーのChatsを右クリック → New chat。Chatの対象選択とInteractiveのモード表示を確認 ブランチやworktreeを作る実装セッションとの違いを理解する
プロジェクトからセッションを始める Projectsで演習用プロジェクトを右クリック → + New session。New worktreeとmainを選ぶ 対象プロジェクト、作業場所、開始元のブランチをそれぞれ確認する
実行するNode.jsを確認する 実装セッションでエージェントにnode --versionの実行を依頼し、ツールの出力を確認 ローカルの確認結果と区別し、テストやビルドを行う環境が要件を満たすか判断する
変更をレビューする 実装セッションのChangesで差分を確認。Create PRからPRを作成 完了報告と実際の差分・テスト結果を照合してからPR作成へ進む
計画を承認する Review plan → Approve and implement this planで承認を送信し、実装へ進む 仕様、対象外の変更、検査方法、作業を止める位置を承認前に判断する
開発画面を見る Run development siteで起動。Browserが自動表示されない場合は、RunターミナルのURLを別ブラウザーで開く。終了時はStopを選択する 起動、ブラウザー表示、停止を別々に確認する。URLと実行中のworktreeも照合する
MCPを使う Customize → Installed → MCP Serversで定義を確認し、Trust repositoryを求められた場合は内容を読んで承認する。Connectedを確認してからセッションでツールを呼ぶ 設定の表示、接続、実際のツール呼び出しを順に確認する。呼び出せない場合は信頼状態と接続設定を調べる
通常マージを判断する Ready to mergeからチェック状態を開き、CI全ジョブの成功後にMerge pull requestで統合する Ready to mergeだけでCI全成功と判断しない。必要なCIと未解決レビューを確認する
Agent Mergeを使う 通常のCreate PRで作成し、最新のCI全ジョブ成功を確認する。Ready to merge横メニューでAgent mergeをOnにする 任せる操作を確認して開始し、AppとGitHubのMerged、最新コミットのCI結果を照合する
Canvasを再利用する プロジェクト共有スコープへ保存・マージし、別セッションで開く。本文追加ボタンからIssue本文を1回追加し、Plan承認後に実装する 表示、更新、共有保存、本文追加を分けて確認する。追加ボタンだけで実装を始めない
Automationを実行する Automations → New automation → Trigger: Manual。Run in the cloudをオフにし、Select project → Create and run → Recent runsでLocal / Succeededと出力を確認する 実行成功の表示に加え、要約の内容をGitHubの一覧と照合する

Agent Mergeを使う前の判断は、第7章の開始前確認に従ってください。CI全ジョブの完了を待つ条件が適用されるかを、対象リポジトリと自分の権限で確認します。条件が不明なら通常のCreate PRで作成し、最新コミットのCI全成功を待ってからAgent Mergeを開始してください。

3. 講師が最新版で確認すること

開催前に、使用するOS、Appの版、確認日を検証状況へ記録します。自分の演習コピーを接続し、上の表に沿って各章の開始状態から入口を確認してください。選択したリポジトリ、セッション種別、権限、実行状態によって表示が違う場合は、その条件と実際の項目名を記録します。

確認では「ボタンが見えた」「操作できた」「期待結果を得た」を分けます。たとえばMCPのConnected表示だけでは、セッションからツールを使えるかは分かりません。ツールを呼び出した後も、フィルターの結果や解除操作まで確かめて初めて、その機能を検証したと判断できます。

機能の意味はGitHub公式のセッション操作、Issue・PR管理、Appのカスタマイズも参照してください。公式の説明と実際の項目名が異なる場合は、対象と操作後の結果を照合して案内します。

現在の未確認範囲は検証状況に集約しています。開催前に必要な操作を確認できなかった場合は、講師デモまたは延期の対象とし、同じ記録へ追記してください。HTMLやPDFの生成検査は、Appの操作確認には含めません。

4. 画像を撮り直すとき

画像は操作例として参照し、最新版の画面とは本文と上の表で照合してください。テンプレート取得先は、本文記載のiwizsophy/dev-days-tailspin-templateを基準に確認します。画像の差し替え状況は検証状況へ記録してください。

撮り直す対象は、次の操作です。優先してIssuesの表示、構成の信頼確認、計画承認を揃えます。

  • 演習用テンプレートのUse this templateと作成フォーム
  • IssuesのOpenビュー、New session、Repository trustの承認
  • セッション開始時のリポジトリ・worktree選択、Changes、Filesによる指示ファイルの閲覧
  • Planのレビューと承認、Runによる起動・URL確認・停止
  • MCPの既存設定・信頼確認・接続状態と、セッションでのツール実行
  • Agent Mergeの開始前確認と許可範囲、共有Canvasの再表示・本文追加、Automationの手動実行結果

本文と同じ演習・開始状態で撮影し、個人情報や非公開情報は写さないようにします。撮影条件と画像の対応はsources.jsonに記録してください。マージボタンの画像だけではCI全成功は伝わらないため、画像から分かる操作と、本文で説明する判断を分けます。撮影後に実際の操作結果と説明を照合してから教材へ反映してください。
