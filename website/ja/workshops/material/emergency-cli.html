教材セットの入口App シナリオの目次 事前準備・UI の確認

講師専用：CLI による緊急の作業保全・続行

この教材セット独自の運営・補助手順です。

本手順は、App の演習を置き換える通常ルートではありません。受講者の操作が停止した場合は、まず App 内で現在の操作を確認し、解決できなければ App の講師デモまたはペア操作で学習を継続します。 CLI は、受講者の作業成果を失わずに実装を進める必要がある場合に限り使用し、その章の App 操作体験は「未完了」として記録します。

判断基準 · 作業場所と PR の確認

演習0の緊急対応：同じ演習コピーを準備する

この章は App および CLI 共通の環境準備です。本文の Tailspin Toys テンプレートから各自のコピーを作成し、そのコピーをローカルに clone します（すでに App 側で clone 済みのフォルダーがある場合は同じものを使い、重複して新しいコピーを作成しないでください）。

Node.js 22.13 以上、Git、および Copilot CLI を準備します。npm を用いる場合の導入例は以下の通りです。

node --version
git --version
npm install -g @github/copilot
copilot --version

各自のコピーで README を確認し、npm ci および npm run dev を実行して、表示されたローカル URL をブラウザーで開きます。E2E テストを実行する場合は、README の指示に従って npx playwright install chromium も実行してください。CLI の認証確認は次章で行います。

合流条件： 各自の演習コピーがローカルで起動でき、Git の remote が自身のフォークリポジトリを指していること。App のインストールが利用できない場合でも、CLI を用いて本編の課題を継続できますが、App 機能の体験は「未実施」と記録します。

演習1の緊急対応：同じプロジェクトについて質問する

共通の切り替え手順 に従って作業場所を確認し、ターミナルで copilot を起動します。認証を求められた場合は各自の Copilot アカウントでログインし、フォルダーの信頼先が演習コピーであることを確認してください。

起動後、次のプロンプトを入力して応答を確認します。

このリポジトリの構成、ゲームデータの取得方法、開発サーバーの起動方法、
テスト・lint・型チェックの方法を説明してください。ファイルは変更しないでください。

合流条件： Tailspin Toys のリポジトリ構成について正しく日本語で応答し、README の記載と回答内容が一致していること。App の Run メニュー、ターミナル、レビュー画面の説明は本文の解説を読み、画面操作体験の未実施を記録した上で、同じコピー環境で演習2へ進みます。

演習2の緊急対応：星評価を表示して最初の PR を作る

共通手順 に従って同じ作業ブランチを開きます。未着手の場合は、クリーンな既定ブランチから feature/app-02-rating などの作業ブランチを新規作成します。CLI に対し、引き継ぎ情報と以下の要件プロンプトを渡します。

Game 型と GameCard.astro、既存の差分を確認してください。
ホームページの各ゲームカードに既存の starRating（5点満点）を表示し、
null の場合は「No rating yet」と表示してください。
カードの構造は組み替えず、実装済みなら重複して追加しないでください。
数値と null のケースを検証し、quality-checks に従って確認してください。
commit・push・PR・merge はまだ行わないでください。

別のターミナルで npm run dev を実行し、ブラウザーで星評価の表示を確認します。通常データ（seed）に null が存在しない場合は、テスト用 fixture 等で表示を検証し、通常の UI 操作で確認した結果と明確に区別してください。

合流条件： 星評価および未評価（null）の表示、関連テストの成功、差分レビューが完了していること。PR・合流の共通手順 に沿って自身のコピーに PR を作成し、CI 成功を確認した上で通常マージします。最新の既定ブランチを取得して演習3へ進みます。

演習3の緊急対応：指示を更新し、コード例で確かめる

演習2の星評価がマージされた既定ブランチから、未使用の feature/app-03-instructions などのブランチを作成して開始します（途中からの切り替えであれば既存のブランチを継続使用します）。自身のコピーにある Update our repository coding standards Issue の内容を確認し、その要件を CLI へ渡します（Issue がない場合は要件を講師と確認し、自身のコピー内に起票します）。

この Issue の要件に沿って .github/copilot-instructions.md を更新してください。
既存の指示を維持し、TSDoc の目的・引数・返り値とファイルヘッダーの標準を追加します。
最初に差分を読み、既に実装済みの部分は維持してください。PR はまだ作らないでください。

指示ファイルの差分をレビューした後、指示が反映されるかを確かめるため、次のプロンプトを依頼します。

ファイルは変更せず、すべての Publishers を返すライブラリコンポーネントの
コード例だけを示してください。更新した指示の TSDoc とヘッダーを反映してください。

合流条件： 指示ファイルと提示されたコード例が要件に一致していること。ここでは CLI 独立コースのように publisher helper の実ファイルを作成する必要はありません。リポジトリの品質確認後、共通手順 に従って PR 作成と通常マージを行います。演習4へは、星評価と指示更新が含まれる最新の既定ブランチから進みます。

演習4の緊急対応：同じフィルター機能を計画・実装する

演習2および演習3の変更を含む既定ブランチから feature/app-04-filtering などのブランチを作成して開始します（App で着手済みであれば、そのセッションと同じ worktree およびブランチを使用します）。自身のコピーのフィルター Issue 本文を貼り付け、/plan（利用できなければ通常の対話）で計画作成を依頼します。

この Issue に従って、カテゴリーとパブリッシャーでゲームを絞り込む計画を作ってください。
星評価を維持し、既存の指示と差分を確認してください。
publisher helper が存在するとは仮定せず、現在の実装から必要な変更を判断してください。
選択方式、複数条件の意味、解除、該当なし、再読み込み時の状態を確認し、
受け入れ条件とテスト計画を示してください。まだ実装しないでください。

計画への質問に回答し、計画内容を確認・合意した後に実装を依頼します。App の Autopilot が利用できなくても、通常の対話で承認を与えて進めることが可能です。

確認した計画を実装し、.github/skills/quality-checks/SKILL.md を読んで
その手順で検証してください。スキルを読み込めたか、実行コマンド、結果、
未確認項目を報告してください。commit・push・PR・merge はまだ行わないでください。

合流条件： 要件に沿ったフィルター機能の実装、星評価の維持、新規コードの指示ファイル準拠、quality-checks の成功、および差分レビューの完了。スキルが呼び出せず同等コマンドを手動実行した場合は、スキル体験を「未実施」と記録します。演習5へは同じブランチを維持し、機能をマージせずに引き継ぎます。

演習5の緊急対応：同じフィルターを Playwright MCP で検証する

演習4の worktree およびブランチをそのまま維持します。別ターミナルで npm run dev を起動し、実際のアクセス URL を確認します。CLI で /mcp show を実行して既存設定を確認し、未登録であれば /mcp add で名前 playwright、種類 STDIO、コマンド npx @playwright/mcp@latest --headless を登録して保存します。

※CLI と App で MCP 設定が自動共有されるとは仮定できません。接続できない場合は CLI の再起動とプロセス状態を確認してください。Chrome が見つからないエラーの場合は npx playwright install chrome を実行します（E2E 用 Chromium とは別物です）。Codespaces で sandbox エラーが出る場合に限り、CLI 参考資料の対処 を確認してください。

Playwright MCP のブラウザーツールを使って [実際の localhost URL] を開き、
演習4で合意したフィルター条件、複合条件、解除、キーボード操作と星評価を確認してください。
期待値と実測値を記録し、不具合があれば修正して再検証してください。
MCP を使えない場合は成功扱いにせず、エラーを報告してください。PR はまだ作成しません。

合流条件： MCP ツールの実行が確認でき、フィルターの受け入れ条件を満たしていること。データ上0件が選べない場合はテストコードで補い、実証拠を区別します。MCP が復旧しない場合は、通常のブラウザー手動操作と自動テストで機能を検証し、MCP 体験は「未実施」と記録して演習6へ進みます（修正後は quality-checks を再実行します）。

演習6の緊急対応：通常の PR レビューとマージ

Agent Merge 自体の動作を CLI の通常操作で体験した扱いにはできません。この章では各自のコピーへの通常マージによってコード統合を学び、Agent Merge の体験は講師デモまたは後日実施とします。

  1. 演習4・5の作業ブランチにおいて、最新の差分と quality-checks の結果を確認します。
  2. PR・合流の共通手順 に沿って各自のコピーに PR を作成します（すでに PR が存在する場合はその PR を更新します）。
  3. base / head、差分、CI 実行結果、レビュー指摘を確認します。失敗があれば同じブランチで修正・再検証し、PR を更新します。
  4. 自身のコピーへの通常マージを実行し、最新の既定ブランチでフィルターと星評価の両方が正しく残っていることを確認します。

合流条件： PR の必要な CI とレビューが成功し、各自のコピーへ統合されていること。マージできない場合は PR の状態と残課題を記録し、演習7において「すべてマージ済み」と安易に仮定しないようにします。Agent Merge の機能体験は別欄に記録します。

演習7の緊急対応：優先順位を文書で整理する

App の共有 Canvas やセッション開始ボタンの挙動を、CLI 上で完全に再現することはできません。本対応では、優先順位の論理的整理と共有可能なドキュメント成果物の作成までを扱います。

各自のコピーの最新 Issue 一覧と PR の状態を確認し（取得できなければ本文を貼り付け）、未使用の作業ブランチを用意して次を依頼します。

この演習コピーの Issue から優先すべき3件を選び、理由と残りの一覧を
docs/workshop-triage.md に日本語で整理してください。既存ファイルがあれば維持して更新します。
Issue の URL、状態、優先理由、次の行動を含め、Issue 自体は変更しないでください。
App の Canvas を作ったという記述はしないでください。PR・merge はまだ行いません。

合流条件： 優先順位、選定理由、および次のアクションを論理的に説明できること。必要に応じて自身のコピーへの通常 PR でドキュメントを共有します。Canvas の共有保存やボタン操作は講師デモまたは後日実施とし、未体験を記録して演習8へ進みます。

演習8の緊急対応：単発の振り返りと終了確認

App の Automation 機能を利用できない場合は、同等の要約処理を CLI で単発実行します（予約・定期実行の代替ではありません）。

この演習コピーで過去1週間にマージされた PR と、現在 open の Issue を要約してください。
取得できなければその旨を報告し、私が貼り付ける情報だけでまとめてください。
ファイル、Issue、PR は変更せず、定期実行も登録しないでください。

要約結果を各自の GitHub Web 表示と照合します。各章の成果、未確認項目、および App 固有機能の体験状況を振り返り、開発サーバーと CLI を停止します。Codespace を使用した場合は演習環境を停止し、作成した定期実行があれば不要なものを停止してください（PR や未保存の作業ツリーは消さずに残します）。

合流条件： 実際の開発履歴に沿った振り返りと環境の終了確認が完了していること。Automation の機能体験は単発要約の実行とは明確に区別して記録します（詳細は 章別検証表 を参照）。
