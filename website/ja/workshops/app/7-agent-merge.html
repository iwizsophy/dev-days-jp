7.1 章の概要

前章までで、フィルター機能の実装、単体・E2Eテスト、Playwright MCPによるブラウザー操作の検証を終えました。次は、この変更をmainブランチへマージし、後続の作業から利用できるようにします。mainへの統合と、本番環境への公開は別の工程です。本章では統合までが対象です。

これまでの手動マージでは、人がCIの完了を待ち、最後のボタンを押しました。Agent Mergeを使うと、PRの確認とマージの操作をエージェントへ任せられます。自動化するときも、何を満たしたらマージしてよいかは人の判断が必要です。

この章では、先にPRを作成してCIの全ジョブ成功を確認し、その後でAgent Mergeを開始します。「マージできる」という表示と、「必要な検証を終えた」という判断を分けて考えましょう。

7.3 取り組む前に

フィルター機能の実装セッションを使い続けます。前章までの差分レビュー、単体・E2Eテスト、MCPによる画面検証と後片付けを終えておいてください。未対応の指摘が残っている場合は、先にその修正と再検証を行います。

GitHubで「マージ可能」であることと、この演習で求める「CIの全ジョブ成功」は同じとは限りません。必須チェックに指定されていないジョブが実行中でも、GitHubはマージを許可する場合があります。保護設定の考え方はGitHub公式の必須ステータスチェックの説明で確認できます。

Agent Mergeは、有効にするとその場で処理を始める仕組みです。マージ可能なPRでは、すぐにMergedへ変わることもあります。開始後に設定を見直すことを前提にせず、差分とCIを先に確認してください。

7.4 体験すること

7.4.1 PRを作成し、最新のCI結果を確認する

  1. 前章まで作業していたフィルター機能の実装セッションを開き、Changesで未対応の差分や不要な一時ファイルがないことを確認します。
  2. 通常のCreate PRでPRを作成します。この時点ではAgent mergeを有効にしません。
  3. 作成されたPRを開き、フィルター機能とその検証に必要な差分が含まれ、自分の演習用リポジトリのmainをマージ先にしていることを確認します。
  4. GitHubのPR画面で、最新コミットに対するCIの全ジョブが成功するまで待ちます。テスト、lint、型検査などに実行中や失敗が残っていないかを見てください。

待つ前に、どのジョブが実行されるかを一覧で見ておきましょう。完了後に同じ一覧を読むと、成功したジョブだけを見て判断していないかを確かめられます。新しいコミットが追加された場合は、古い成功結果を使わず、そのコミットのCIを確認し直してください。

AppのCI表示が更新されない場合は、PRの画面を開き直して確認します。GitHub側の最新結果とも照合してください。Ready to mergeだけで、CIの全ジョブ成功とは判断しません。

7.4.2 Agent Mergeを開始する

  1. 差分レビューと最新コミットのCI全成功を確認したら、同じセッション上部のReady to merge横にあるメニューを開きます。
  2. 対象が今回のフィルター機能のPRであることを確認します。
  3. Agent mergeのスイッチをOffからOnへ切り替えます。この操作で処理が始まるため、追加の開始ボタンを押す必要はありません。

GitHub公式では、Agent MergeがPRを確認し、マージを妨げる問題へ対応して、GitHubが許可した時点でマージすると説明しています。公式説明「Merging a pull request」

7.4.3 CIとマージ結果を確認する

  1. AppのセッションまたはPRの画面がMergedになったことを確認します。
  2. GitHubでも同じPRを開き、mainへMergedになったことと、最新コミットのCI全ジョブが成功したことを照合します。
  3. エージェントがレビュー対応やCI修復のためにコードを変更した場合は、その差分と変更後の検査結果も確認します。
  4. 次章で新しいworktreeを作るときに、このフィルター機能のマージ結果を継承できるよう、mainへ統合されたことを確かめます。

画像はマージ後の表示例です。受講者ごとのPR番号を確認し、自分のPRの結果と照合してください。

7.5 結果の整理と振り返り

完了したら、次の3点を自分の言葉で説明してみてください。Agent mergeをOnにしたこと、CIが成功したこと、マージが完了したことを区別できれば、途中で問題が起きた場合にも確認箇所を絞れます。

振り返る問い 今回の結果で確かめること
人は何を判断したか 要件を満たす差分、レビュー結果、マージ先、最新CIの全成功
エージェントへ何を任せたか CI確認後のPR確認とマージの操作。追加修正があれば、その内容も区別する
完了を何で説明できるか AppとGitHubのMerged、マージ先のmain、成功したCIの一覧

今回はCIを待つ工程を人が担当しました。追加修正が起きなかった場合は、CI失敗や競合の修復を体験したとは扱わず、実際に任せた操作を振り返ります。自動化の機能名だけでなく、任せた範囲と確認した結果を説明できることが到達点です。

次は、課題を同じ画面で比較し、エージェントと作業を計画するキャンバスを使います。第8章「キャンバスを使った計画」へ進んでください。

7.6 補足

7.6.1 手動マージの経験を自動化に生かす

本ワークショップでは、コード生成、自動テスト、MCPによる実ブラウザー操作と、段階的に任せる操作を広げてきました。星評価やコーディング標準を手動でマージしたのは、差分、CI、マージ先を自分で確認するためです。その経験があれば、自動化するときも何を任せたかを説明できます。

今回は第5章で計画と実装をレビューし、第6章で実画面を検証したうえで、mainへのマージをエージェントへ渡しました。任せる範囲を広げても、要件を満たす変更かどうかを判断する責任は人に残ります。

7.6.2 任せる範囲と品質確認

Agent Mergeはバックグラウンドで動作し、Appの再起動後も継続して、マージ後に終了します。待機やマージの操作を任せても、テストに含まれていない要件まではCIの成功だけで判断できません。GitHub公式のAgent Mergeの説明

たとえば、カテゴリを2つ選んだときに片方の結果しか表示されない実装でも、件数を十分に検査していなければテストを通ることがあります。前章までのレビューで確認した条件を、自動化後も品質の基準として使ってください。

詳細な操作許可を選べる場合は、次の観点で任せる範囲を確認します。許可した機能と、実際に行われた処理は区別してください。

任せる操作 人が確認すること
レビュー指摘への対応 指摘の意図を満たし、不要な仕様変更を加えていないか
CI失敗の調査と修正 検査を弱めて通していないか。修正後に必要な検査を実行したか
他の変更との競合解消 両方の変更意図を保っているか
条件を満たしたPRのマージ 対象PRとマージ先が正しく、レビューと検証を終えているか

CIの待機も含めて任せたい場合は、必要なチェックを待つ条件が、自分の権限でのマージにも適用されるかを先に確認します。条件が分からなければ、本章と同じく全ジョブの成功を待ってから開始してください。ブランチ保護や必須チェックの設定を理解すると、チームでどこまで任せるかを判断しやすくなります。GitHub公式のブランチ保護の説明
