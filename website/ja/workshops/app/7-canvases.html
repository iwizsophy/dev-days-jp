この章の確認範囲： 2026年9月13日に Windows の App 1.1.20 実機にて、キャンバスの作成、プロジェクト共有スコープでの保存、Agent Merge によるマージ、別セッションでの再表示、および Issue のセッションコンテキスト追加を確認済みです。さらに、通知の反復送信バグを修正したうえで、キャンバス経由で追加した検索 Issue の計画立案・実装・MCP 検証・Agent Merge（PR #15）までの一連の流れを追加実走しています。

ここまでのレッスンでは、主にチャット（会話）を通じてエージェントに指示を出してきました。しかし、実際のソフトウェア開発では、会話だけでなくカンバンボード、設計ドキュメント、リリースチェックリストといった「成果物の領域」を共有しながら作業を進める場面が多く存在します。

キャンバス（Canvas）は、まさにそうした具体的な作業成果物をアプリ内で人間とエージェントが直接共有・操作するための専用領域です。本レッスンでは、残りのバックログを効率的にトリアージし、作業を追跡するためのシンプルなカンバンボードキャンバスを作成します。

このレッスンでは、次の内容を学習します。

  • キャンバスの概念と、チャット対話との使い分けを理解する
  • バックログをトリアージするための共有カンバンボードキャンバスを作成する
  • キャンバス定義をプロジェクト共有アセットとしてリポジトリに保存し、マージする
  • 新しいセッションでキャンバスを開き、ボードから直接タスクを着手する

シナリオ

大量の Issue が並ぶバックログは、優先順位の判断が難しくなりがちです。Tailspin Toys の開発チームは、Issue を迅速にトリアージし、必要な作業をスムーズに Copilot app のセッションへ取り込んで着手できる対話型ツールを求めています。

キャンバスとは

キャンバス（Canvas）は、実装計画、タスク管理ボード、リリースチェックリスト、ダッシュボードといった作業成果物を扱う、共有の対話型作業領域です。チャットは要件のすり合わせや曖昧さの解消に適していますが、構造化された成果物の作成や管理には専用の作業台（スペース）が必要です。キャンバスを用いることで、エージェントと同じ成果物領域上で直接共同作業が可能になります。

キャンバスは双方向（Interactive）に操作できます。エージェントが作業の進捗に合わせてキャンバスの内容を更新できるだけでなく、人間側も同じ画面上で直接要素を編集・操作できます。指示プロンプトに基づいて初期レイアウトを生成させた後も、対話を通じて機能の追加、削除、レイアウト調整を継続的に依頼できます。作成されたキャンバスは、アプリの右パネルに展開されます。

代表的なキャンバスの活用例は次の通りです。

  • Markdown canvases：日々の開発計画を整理し、Issue や PR の優先順位を俯瞰する
  • Agentic kanban boards：ユーザーとエージェントがカードを追加し、作業フェーズに応じて列間をドラッグ移動する
  • Issue triage boards：リポジトリ内の重要 Issue や頻出するテーマを集約・分類する

キャンバスを使用する理由

タスクに明確な構造化、反復的な更新、視覚的な追跡が求められ、チャットの会話ログだけでは一覧性が不足する場合にキャンバスが効果を発揮します。

  • 開発ワークフローに即した具体的な成果物に対してエージェントの作業を結びつけられる
  • 共有画面上で人間が直接配置や優先度を修正し、その結果をエージェントに認識させて作業を継続できる
  • 会話文の応答だけでなく、目に見える成果物の変化として進捗を直感的に把握できる

作業を追跡するキャンバスを作成する

星評価、コーディング標準、フィルター機能のリリースを完了しましたが、バックログにはまだ対応すべき Issue が残っています。残課題を迅速にトリアージするためのキャンバスを作成しましょう。

  1. GitHub Copilot app を開きます。
  2. サイドバーの演習用リポジトリの横にある New session を選択します（App 1.1.20 では New 画面が開きます）。
  3. 入力欄下部で演習用リポジトリが選ばれており、New worktree および main が指定されていることを確認します。作成された worktree に前章のマージ結果が正しく反映されていることも確認してください。
  4. 次のプロンプトを入力し、カンバンボードの作成を指示します。
作業の優先順位をすぐに整理できる、基本的なカンバンボードの canvas を作ってください。今対応すべき上位3件の Issue を強調し、残りは下の別の領域に配置してください。上位3枚のカードには Issue の内容と優先する理由を含めてください。各 Issue に、現在のセッションのコンテキストへ追加してすぐ作業を始められるボタンを付けてください。

Copilot がキャンバスの作成処理を開始します。

実機検証における作成挙動

実走検証では、右パネルに Issue triage board が開き、未対応の Issue 6件が「上位3件」と「残り3件」の2つの領域に分類されて描画されました。
なお、初版生成時点では上位3件のカードにしか操作ボタンが配置されていなかったため、「すべてのカードに Add to current session ボタンを配置してください」と追加で指示を出して修正させました。画面に描画されたことだけで完了とせず、カードの総数、優先理由の妥当性、更新ボタンの有無、および各カードのボタン動作を必ず確認してください。

補足 キャンバスの生成には数分を要する場合があります。複雑な UI 構築タスクであるため、1回目の生成で完全な状態にならないこともあります。求めている操作性になるまで、チャットを通じて追加の要望を伝え、反復的に修正を指示してください。

キャンバスを保存してリポジトリにマージする

作成したキャンバスは、指示ファイルやスキルと同様に、リポジトリの恒久的な開発アセットとして管理できます。キャンバスの定義ファイルをリポジトリへコミットし、チーム全体で共有できるようにマージしましょう。

  1. 同一セッション内で、次のプロンプトを入力してキャンバス定義の保存を依頼します。
開発チームと共有できるよう、この canvas の定義をリポジトリに保存してください。
  1. エージェントがキャンバスファイルを保存したら、ファイルの保存場所を確認します。

保存先スコープの確認：

  1. 画面右上にある Create PR 横のドロップダウンから Agent merge を選択します（すでにボタンが Agent merge になっている場合はそのまま次へ進みます）。

キャンバスで作業する

マージされたキャンバスを、新しいセッションから呼び出して実際の開発作業に着手してみましょう。

  1. サイドバーで演習用リポジトリの横にある New session を選択し、新しいセッションを開始します。
  2. 次のプロンプトを入力し、保存したキャンバスを開かせます。
Issue の優先順位を整理する canvas を開いてください。
  1. 作成したトリアージボードキャンバスが右パネルに表示されることを確認します。
  2. 着手したい Issue（例: タイトル検索機能）のカードにある Add to current session ボタンをクリックします（ボタン表示名はキャンバスの実装によりますが、実機ではこの表記でした）。
  3. Issue の詳細内容が会話欄に1回だけ送信され、エージェントから受信の確認応答が返ることを確認します（ボタンの役割はあくまでセッションコンテキストへの追加です）。
  4. 実装計画を立てるため、入力欄下部のモードを Mode: Interactive から Plan に切り替えます。実機検証では「キャンバスから追加したタイトル検索 Issue の実装計画を作成し、既存のフィルター機能と星評価を維持してください」と指示しました。

  1. 提示された計画を Review plan で確認し、Approve and implement this plan → Continue を選択します。セッションが Autopilot に切り替わり、実装が開始されます。

  1. 実装完了後、Changes で差分をレビューし、テストおよびブラウザーでの検証を指示します。実機検証では、SQL 検索におけるワイルドカード文字（% や _）のエスケープ不備をレビュー時に指摘・修正させ、単体テスト39件、E2Eテスト28件、キャンバス回帰テスト3件、lint、型検査、build の全通過を確認しました。さらに Playwright MCP を用いて、通常データ21件での検索、複合条件、検索結果0件、およびキーボード操作による解除も確認しています。
  2. 問題がなければ、前章で習得した Agent merge を指定して PR 作成とマージを委託します。検証用 PR #15 は CI 全4ジョブ通過後に自動マージされ、検索機能の Issue #1 が正常にクローズされました。
  3. キャンバス右上の Refresh ボタンをクリックし、完了した Issue がボードの未対応一覧から除外されることを確認します。

実機検証におけるトラブルシューティングと確認事実

補足 反復送信バグへの対処記録： 初版のキャンバスでは、ボタン押下時に「この Issue をセッションに追加してください」という命令形の通知メッセージを会話欄へ送っていたため、これを受け取ったエージェントが自身で追加アクションを再帰的に呼び出し、同一メッセージが無限ループで送信されるバグが発生しました。 - 緊急対応：セッションの Stop で処理を強制停止。 - 改修内容：通知文言を「Issue を追加しました」という客観的な事実通知へ変更。さらに、同一 Issue の送信中・送信済み状態をフラグ管理し、再入時には即時リターンする制御ロジックと回帰テストを追加。 - 結果：1 回のクリックで正確に 1 通知・1 応答となり、ボード Refresh 後の再クリックでもメッセージが増殖しないことを実機で確認しました。

補足 ボード手動更新の仕様： 追加実走検証では、Add tab → Canvas → Issue triage board から再度ボードを開き、Refresh をクリックした後に 5 open issues loaded. と表示され、未対応の Issue（#2〜#6）のみが正しく描画されることを確認しました。 すでにクローズされた検索（#1）、フィルター（#7）、指示更新（#8）は一覧から除外され、GitHub 上の最新ステータスと一致しています。なお、PR マージの完了通知だけでボードが自動更新される仕様ではないため、明示的な Refresh 操作後の表示照合をもって検証完了としています。

これで、キャンバスを活用した高度なタスク管理と自律エージェントの協調フローを確立できました。

注意 講師向け緊急対応： 参加者の環境でトラブルが生じ、緊急に作業を保全する必要がある場合のみ 講師専用 CLI 対応手順 を参照してください。なお、CLI 側で実装が完了しても、本章における App 操作の完了実績とは見なしません。

まとめと次のステップ

人間とエージェントが双方向で操作できる共有作業領域（キャンバス）を構築し、実際の開発フローに統合しました。本章で実施した主な内容は次の通りです。

  • キャンバスの概要と、チャットの限界を補完する視覚的共有領域の価値を理解した
  • バックログをトリアージするための共有カンバンボードキャンバスを作成した
  • キャンバス定義をプロジェクト共有アセットとしてリポジトリに保存し、Agent Merge でマージした
  • 新しいセッションでキャンバスを開き、カードから直接タスクをセッションに投入して機能実装・検証・マージを完走させた

バックログの管理と実装の自動化を体験できました。次の最終レッスンでは、ワークショップ全体で構築した成果と技術を振り返り、自組織での実践に向けたロードマップを確認します。レッスン 8「振り返りと次のステップ」 へ進んでください。
