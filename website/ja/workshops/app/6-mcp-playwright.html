6.1 章の概要

単体テストやスクリプト化されたエンドツーエンドテストに加えて、開発中のUIをユーザーの操作に沿って検証します。エージェントへブラウザーの操作手段を与え、選択欄やボタンを操作したときに、新機能が仕様どおりに動くかを確かめます。

6.2 この章で学ぶこと

MCPを通じてブラウザー操作を依頼し、その履歴と観察結果で機能を確認することが、この章の到達点です。

学ぶこと 到達した状態
MCPの接続確認 設定の登録、接続表示、実際のツール呼び出しを区別できる
探索的なブラウザー検証 条件を変えて操作し、期待結果と実際の表示を比べられる
結果報告のレビュー 件数・タイトル・選択状態を操作履歴と照合し、未実施の確認を補える
検証環境の終了 通常データと成果物を残し、今回の一時ファイルとサーバーを片付けられる

6.3 取り組む前に

前章のフィルター実装セッションを開いたまま使います。単体テスト、E2E、lint・型検査とbuildを確認し、通常の21件と、0件表示を試す隔離データ3件を区別できる状態から始めます。PRの作成とマージは次章で行います。

テンプレートの.mcp.jsonにはPlaywrightが定義されています。すでに利用できる設定を確認してから進めましょう。MCP serverは外部のプログラムや接続先へ操作を渡す仕組みです。定義のコマンドと接続先を読み、信頼の承認を求められたら内容を確認します。演習では、自分のworktreeで起動したサイトを検査対象にします。

自動テストが成功していても、MCPで指定した操作がすべて実行されたとは限りません。操作前に表示を予想し、戻ってきた結果とツールの履歴を比べて確認します。

6.4 体験すること

Playwrightの接続を確かめ、通常環境と隔離環境でブラウザーを操作します。報告に不足があれば確認を補い、使った環境を最後に終了させてください。

6.4.1 Playwright MCPの接続を確かめる

Appの公式ドキュメントでは、リポジトリやCopilot CLIに設定したMCP serverをAppでも利用できると説明されています。登録済みのサーバーはCustomize → Installedで管理します。

  1. フィルター実装セッションのFilesで.mcp.jsonを開き、mcpServersにあるplaywrightの定義を読みます。npxでローカルプロセスを起動するコマンドと引数を確認してください。ほかの定義は、今回必要なPlaywrightと区別して読みます。
  2. サイドバーのCustomizeを開き、InstalledのMCP Serversで登録済みのPlaywrightを確認します。表示される設定の適用先も読み、既存の接続があれば重複して追加しません。設定画面が見つからなければ、講師に相談してください。

  1. Trust repositoryなどの承認を求められた場合は、実行するコマンドや接続先を読み、内容を確認して承認します。信頼状態とサーバーの接続状態をそれぞれ確かめてください。
  2. フィルター実装セッションに戻り、次のプロンプトを送信します。
このセッションで利用できるPlaywright MCP serverのbrowser_tabsを使って、ブラウザーのタブ一覧を取得してください。接続確認だけを行い、ファイルは変更しないでください。
  1. ツールの呼び出しと結果を開き、タブ一覧が返ったことを確認します。about:blankは開いているタブの状態で、フィルターの検証結果ではありません。

Connectedは接続状態の表示です。演習に必要なツールがセッションから使えるかは、実際の呼び出し結果で確かめます。呼び出せない場合は、補足の再接続・追加登録を参照してください。

6.4.2 Playwrightでブラウザーを操作する

前章から開いたままにしているフィルター機能の実装セッションに戻り、Playwright MCP serverを使って新機能の動作を手動検証するようCopilotに指示します。

  1. 会話入力欄に次のプロンプトを入力して送信します。
このセッションで実装したフィルター機能を、Playwright MCP serverで検証してください。今回のworktreeから開発サーバーを起動し、接続したURLを報告してください。
前章で保存したテスト用CSVと準備スクリプトを使い、隔離テスト用の一時DBを作り直してください。通常CSVと通常DBは変更せず、テスト用DBを接続先に指定して隔離環境のサーバーを起動してください。
Issueと承認済みの計画を使い、カテゴリの複数選択、出版社との組み合わせ、解除、キーボード操作を確認してください。通常データではStrategyのみ4件、StrategyとPuzzleのORで8件、そこへGitHub Gamesを加えると2件、解除で21件を確認してください。カテゴリ未選択のGitHub Gamesのみ5件、CodeForge Studiosのみ6件も確認してください。
カテゴリをSpaceで選択・解除し、PublisherからTabでClear filtersへ移ってEnterで解除する操作を、クリックや直接フォーカス移動へ置き換えずに確認してください。前章で用意した隔離テストデータでは、初期3件、PuzzleとNova Interactiveで0件、解除で3件を確認してください。
通常データと隔離データを分け、操作・期待結果・実際の件数とタイトル、選択状態を報告してください。
検証後はbrowser_closeでブラウザーを閉じ、今回起動したサーバーを停止してください。今回作成した一時DBとMCP出力だけを片付け、テスト用CSV・テストコードや既存の成果物は残してください。実施できなかった項目も明記してください。PR作成・マージは次章まで待ってください。
  1. CopilotはPlaywright MCP serverを通じてブラウザーを自律起動し、検証ステップを順次実行して結果を会話欄に報告します。タスク実行中、環境によってはデスクトップ上で実際にブラウザーウィンドウが開き、自動操作される様子が視覚的に確認できます。
  2. 報告された概要をIssueの受け入れ条件と照らし合わせてレビューします。もし挙動に問題があれば、PRを作成する前に追加の指示を出してコードを修正させてください。

「問題ありませんでした」という概要だけでは、何を確認したか判断できません。どのカテゴリと出版社を選び、何件・どのゲームが表示されたか、どのキーで解除したかを確認します。ツール呼び出しと結果も開き、実際の操作から得た報告かを読み取ってください。コードを直した場合は、影響する自動テストとブラウザー操作を再確認します。報告が「未実施なし」でも、表の操作に対応する履歴が見つからなければ、実際にその操作を行うよう補足してください。

  1. 次章のAgent Mergeで同じ変更を共有するため、このセッションは開いたままにします。

6.4.3 操作結果を受け入れ条件と比べる

ツールの履歴から、ページへの移動、選択欄やボタンの操作、キー入力といった流れを読み取ります。確認の対象は、必要な操作と観察結果です。ツールの名前や順序を例と同じにする必要はありません。

教材の通常データで確認する操作と期待結果は、次のとおりです。

操作 期待結果 確認する意味
初期表示 21件 通常データの一覧を表示している
Strategyを選択 4件 一つのカテゴリで絞れる
Puzzleも追加選択 8件 カテゴリ同士のOR条件で、両カテゴリが含まれる
GitHub Gamesも選択 2件 カテゴリと出版社のAND条件で絞れる
Clear filtersで解除 21件 選択状態と一覧が初期状態へ戻る
カテゴリ未選択でGitHub Gamesを選択 5件 出版社だけでも絞れる
カテゴリ未選択でCodeForge Studiosを選択 6件 出版社名を変えた結果を区別できる

表の操作を実行した順に照合し、条件ごとのタイトルも読みます。カテゴリをSpaceで変更した際には、チェック状態と表示の変化を両方確認してください。

通常データが同じでも、選択した出版社が異なれば期待件数は変わります。「出版社単独6件」のように名前を省かず、選択値と件数を一緒に記録してください。

キーボード操作では、カテゴリをSpaceで変更できるか、現在の選択状態が分かるかも確認します。PublisherからTabを使ってClear filtersへ移り、Enterで解除して21件へ戻る操作も試してください。クリックで解除できることだけでは、キーボードでボタンへ到達して操作できることの確認にはなりません。

6.4.3.1 該当 0 件表示の検証について

通常データセットには全カテゴリーと全パブリッシャーの組み合わせに必ず該当ゲームが存在するため、通常の絞り込み操作のみでは「該当件数 0 件」の画面を再現できません。

前章で用意した3件の専用CSVと隔離SQLiteを使い、通常環境とは別ポートのサーバーで検証します。まずテスト用の3件を表示し、PuzzleとNova Interactiveを組み合わせると0件となることを確認します。0件の説明と結果通知を読んだら、Clear filtersでテスト用の3件へ戻ることまで確かめてください。通常環境へ戻ったときの21件と、隔離環境で解除した後の3件を混同しないでください。

0件表示のために通常のdb/games.csvや通常DBを変更しないでください。報告にデータの種類、接続URL、初期件数、選択した条件、解除後の件数があれば、別の環境を検査していないかを見分けやすくなります。

6.4.4 検証に使った環境を片付ける

ブラウザーを閉じても、開発サーバーや一時DBが残っている場合があります。次の検査が古いサーバーへ接続しないよう、今回起動したものを終了させてください。browser_close、サーバー停止、一時DBとMCP出力の削除を確認し、今回使ったポートに待受が残っていないことも照合してください。テストを再実行するためのCSVやテストコードは成果物なので、片付ける一時ファイルと区別します。

最後にChangesを開き、検証のためだけのDBやMCP出力が、共有する変更に混ざっていないかを確認してください。

6.5 結果の整理と振り返り

操作、期待結果、実際の結果、残る未確認項目を整理します。次の項目を、自分のツール履歴と報告に照らし合わせてください。

  • Model Context Protocol (MCP) の基本構造と、アプリに外部ツール（tools / resources）を連携させる仕組みを理解した
  • 既存のPlaywright MCP serverの設定と信頼状態を確認し、セッションから実際にツールを呼び出した。必要な場合の追加登録・再接続方法も確認した
  • エージェントにブラウザーを自律操作させ、フィルター機能の絞り込み、複合条件、キーボード操作、解除、および0件表示を検証した

受け入れ条件の確認と後片付けを終えたら、次章へ進みます。次章では、自分でPRを作成して最新のCIがすべて成功したことを確認し、Agent Mergeへマージを任せます。mainへの統合結果を確認するところまでが、この演習の範囲です。第7章「Agent Mergeによるマージ」 へ進んでください。

次へ進む前に、MCPで初めて気づいた点と、既存のE2Eテストでも確認していた点を比べてみてください。今回確認した操作・結果・残る未確認項目を整理すると、次章でPRをレビューする根拠として使えます。

6.6 補足

6.6.1 探索的な検証とE2Eテスト

前章では、プロジェクトに組み込まれた自動テストスイート（単体テストやE2Eテスト）を用いてフィルター機能を実装・検証しました。自動テストに加えて、エージェントが実際のブラウザーを対話的に操作し、その結果を読み取れるようにすると、テストにまだ書いていない操作順序や表示状態も調べられます。操作できない要素や期待と違う結果があれば、その場で原因を調べ、修正と再確認へ進めます。

この章で行うのは、エージェントの観察結果から次の操作を決める探索的な検証です。一方、前章のE2Eテストには、決めた操作と期待結果を保存して繰り返し検査する役割があります。MCPで一度成功した操作が、そのままテストコードとして残るわけではありません。新しい不具合を見つけて修正したら、今後も確認すべき条件をE2Eテストへ追加するか検討します。

6.6.2 Model Context Protocol (MCP) とは

Model Context Protocol (MCP)は、AIエージェントが外部のツールやサービスと情報をやり取りするためのオープンなプロトコルです。MCPを導入すると、エージェントは外部システムと対話し、リソース（resources）を通じて情報を取得したり、ツール（tools）を通じてユーザーに代わる操作を実行したりできます。実際に利用できる情報や操作は、接続先と付与された権限によって決まります。

エージェントは、MCP serverを経由してツールやリソースへアクセスします。MCP serverは、ローカルのプログラムやリモートAPIとの通信を仲介するプログラムです。各サーバーで利用できる操作や情報は異なります。

代表的なMCP serverには次のようなものがあります。

  • GitHub MCP Server：GitHubの各種APIにアクセスするツール群を提供します。エージェント自身によるリポジトリの作成・更新、IssueやPRの管理などが可能になります。
  • Playwright MCP Server：Playwrightを用いたヘッドレス／有頭ブラウザーの自動操作機能を提供します。エージェント自身がページ遷移、フォーム入力、ボタンのクリック、DOMスナップショットの取得などを実行できます。

GitHubは、コミュニティによる発見と貢献を促進するため MCP registry をホストしており、多種多様なMCP serverが公開されています。

6.6.3 Playwrightが画面を読み取る仕組み

本演習で接続するPlaywright MCPは、主に構造化されたアクセシビリティスナップショットを使ってページを読み取ります。ボタンの名前や役割、選択状態などを調べ、クリックやキー入力のツールを呼び出します。Microsoftの公式READMEにこの動作が説明されています。画面のピクセルを見てすべての見た目を判定する仕組みではないため、色や配置などの見た目は、必要に応じてスクリーンショットや人間の画面確認でも確かめます。

接続の確認手順へ戻る

6.6.4 接続できない場合に確認すること

No MCP servers loadedと表示される場合は、リポジトリの信頼状態と.mcp.jsonの形式を確認してください。公式のリポジトリ別設定形式では、定義をmcpServersフィールドに記述します。serversなど別のキーになっている場合は修正が必要ですが、教材テンプレートはこの形式になっているため、通常は編集不要です。

設定を修正した場合は、CustomizeのInstalledへ戻り、接続状態を確認します。上記の公式リンクは設定ファイル形式の参照先です。CLI用の設定コマンドと、Appの画面上の操作を混同しないようにしてください。

6.6.4.1 セッション再起動（/restart-session）の活用

信頼状態と接続設定を確認しても、開いているセッションからPlaywrightのツールを呼び出せない場合は、会話入力欄から/restart-sessionを送信して再接続を試せます。App公式のスラッシュコマンド一覧では、履歴を保持して現在のセッションを再起動するコマンドと説明されています。ツールを呼び出せている場合、この操作は不要です。

6.6.5 Playwrightが未登録の場合に追加する

既存のPlaywrightを利用できない場合に、GUIから追加する手順です。接続とツール呼び出しを確認済みなら追加は不要です。App公式の手順も、CustomizeからMCPを探し、Installedで登録済みの設定を管理する流れを説明しています。

  1. サイドバーの Customizeを開きます。
  2. Installedタブの MCP Serversで既存の登録一覧を確認します。すでに登録済みの場合は重複して追加しないよう注意してください。
  3. 未登録の場合はMCPタブを開き、Playwrightを探します。Featuredセクションに見つからなければ、Search MCP serversから検索してください。
  4. Playwrightカードを選択して登録フォームを開きます。ローカルで起動する設定例は、Server nameが playwright、Typeが Local、Commandが npx、Argumentsが -y @playwright/mcp@latest です。
  5. 入力内容を確認し、Add serverをクリックして保存します。Installedの一覧に追加されたことを確認してください。
  6. チャットやセッションから実際のツール呼び出しを確かめます。たとえばPlaywrightのbrowser_tabsでタブ一覧を取得するよう依頼し、結果が返るかを確認します。応答にabout:blankが含まれていても、それは開いているタブの状態です。接続できたら、ブラウザー検証の手順へ戻ります。

画像は既存設定の内容を読む例です。新規追加の手順では、保存後の一覧と実際の呼び出し結果まで確認してください。

補足 サイドバーは左上のトグルボタンまたはCtrl+Bで開閉できます。CustomizeやMCPのメニュー項目が見当たらない場合は、Appのバージョン、組織ポリシーによる制限、および現在の画面状態を記録し、講師と一緒に確認してください。
