この章の進め方 ゲームカードへの星評価の表示を依頼し、差分、画面、テストを確認します。最後にPRを作成して手動でマージし、エージェントとの開発の流れを体験します。

前のレッスンでは、ワークスペースの確認とクイックチャットの利用を行いました。本章では、いよいよエージェントセッションを開始し、プロジェクトに最初の変更を加えます。

今回の変更は小規模なものに留めます。ゲームのデータ構造にはすでに星評価が含まれていますが、ホームページのゲームカードにはまだ表示されていません。そこでエージェントにカードへの評価表示を依頼し、生成された変更をレビューしたうえで、最初の pull request としてマージする一連の流れを体験します。

このレッスンでは、次の内容を学習します。

  • エージェントセッションを開始し、その構成要素を理解する
  • プロジェクトに対し、小規模で対象を絞った変更を加えるようエージェントへ依頼する
  • ワークスペースの差分ビュー（Changes）で変更内容をレビューする
  • アプリをローカルで実行し、ブラウザー上で変更結果を確認する
  • 最初の pull request を作成してマージする

シナリオ

Tailspin Toys の各ゲームには星評価のデータが保持されており、ゲーム詳細ページにはすでに表示されています。一方、ホームページの一覧カードにはタイトル、カテゴリー、パブリッシャー、説明文のみが表示されており、星評価は含まれていません。

そこで、最初のエージェントセッションの準備運動として、ホームページの各カードにも既存の星評価を表示するようエージェントに依頼します。対象が絞られており自己完結しているため、エージェントとの最初の共同作業として最適な課題です。

この課題では、データを新しく集めたり保存方法を変えたりせず、すでにある値を一覧にも届けます。画面上の変更が小さいほど、依頼した範囲と生成された差分を比べやすくなります。同時に、「値が0」と「まだ評価がない」の違いのように、小さな表示にも仕様の判断が含まれることを学びます。

セッションの構造

セッションとは、特定のプロジェクトを対象としてエージェントと対話を行う作業空間です。サイドバーのプロジェクト一覧から起動できます。

GitHub公式のセッション手順では、新しいworktree、ローカルリポジトリ、クラウドの実行環境を選べます。本章では New worktree を選び、mainを基にした別の作業場所で変更します。worktreeを分けることは作業中のファイルを分けるためであり、変更が自動的にmainへ反映されるという意味ではありません。レビューとPRのマージを経て、次章で利用できる状態にします。

注意 作業ディレクトリとブランチの確認： 実行場所にローカルリポジトリを選ぶと、既存の作業フォルダーを使います。本章では New worktree が選ばれていることを確かめてから編集を始めます。

  • コード編集を始める前に、作業ディレクトリと現在のブランチを必ず確認する
  • 同一の checkout を共有する複数セッションで同時に編集を行わない

各セッションの画面は、主に次の 3 つの要素で構成されています。

  1. 会話（Chat）：エージェントに対する指示や対話のログ
  2. ツールアクティビティ（Tool Activity）：ファイルの調査や編集時にエージェントが実行した操作履歴
  3. 変更済みファイル（Changes）：差分（diff）付きで確認できる変更ファイル一覧

セッションを開始して変更を依頼する

新しいセッションを開始し、プロジェクトの調査と機能の実装を進めましょう。前のレッスン で GitHub リポジトリから追加した演習用プロジェクトを選択し、変更を依頼します。

  1. GitHub Copilot app を開きます（起動済みの場合はそのまま進めます）。
  2. サイドバーの Projects で、演習用プロジェクトを右クリックし、メニューの + New session を選択します。
  3. New 画面の入力欄下部に、自分の演習用プロジェクト名が表示されていることを確認します。実行場所は New worktree、開始元は main を選びます。モードは、応答を読みながら指示を加える Interactive で進めます。

Interactive・Plan・Autopilotの違いは公式のモード説明で確認できます。

実装前の環境確認

ローカルのターミナルとAppのセッションでは、実行するNode.jsが異なる場合があります。これからテストやビルドを行うセッションで確認すれば、実装後のエラーが環境によるものか判断しやすくなります。

  1. 機能の実装を依頼する前に、次のプロンプトを送信します。
このセッションで node --version を実行し、コマンドの出力をそのまま報告してください。
作業ディレクトリと現在のブランチも確認してください。
ファイル変更、追加インストール、PR作成はしないでください。
  1. ツールの実行結果で、Node.js 24系の24.19.0以降が使われていることを確認します。作業ディレクトリとブランチも、今回のworktreeのものか確かめます。コマンドが見つからない場合や要件を満たさない場合は、前章までのNode.jsの準備を見直します。Node.jsを切り替えた後はAppを再起動し、このセッションで再確認してから実装へ進みます。

エージェントの説明に書かれたバージョンを、ツールのコマンド出力と照合します。環境の確認ができたら、同じセッションで星評価の実装を依頼します。

星評価の実装を依頼する

  1. 次のプロンプトを入力し、変更を依頼します。
ゲームカードに各ゲームの星評価を表示してください。
Game 型には starRating があり、5点満点の数値、または未評価を示す null が入ります。
src/components/GameCard.astro の各カードに表示し、null の場合は「No rating yet」と表示してください。
0は評価値として表示し、未評価と区別してください。
詳細ページの既存の評価表示と関連コンポーネントを確認し、再利用できるものを使ってください。
変更は小さく保ち、カードの構造やゲーム詳細へのリンクは組み替えないでください。
通常データを変更せず、GameCardの実際のレンダリング結果で4.2、0、5、nullの表示とリンク構造をテストしてください。
利用するNode.jsのバージョン、変更内容、実行したテストと結果を報告してください。
PR作成とマージは、後で指示するまで行わないでください。

補足 プロンプトでは更新対象ファイルと期待する表示を指定しています。ファイル指定は必須ではありませんが、変更範囲を共有すると、レビュー時にも目的に沿った変更か確かめやすくなります。既存実装の調査を依頼しているのは、同じ評価表示を別々に作り、一覧と詳細で表示が食い違うことを避けるためです。

今回は「何を表示するか」「既存の何を保つか」「どう確かめるか」を一緒に伝えます。たとえば、星が見えるだけでは null の扱いやリンクの維持までは分かりません。実装前に受け入れ条件を具体化しておくと、完了報告を読んだ後に確認する対象も明確になります。

  1. Enter キーを押して、プロンプトを送信します。

セッション開始後、エージェントがコードベースを調査し、星評価の表示に必要な修正を加えます。なお、エージェントの完了報告テキストだけを鵜呑みにせず、必ず次の手順で実際の差分とテスト結果を自ら確認しましょう。

差分をレビューする

AI が生成した変更は、どれほど小さく見えても、マージ前に人間の目でレビューする必要があります。Copilot app の機能を使って差分を確認しましょう。

  1. 会話入力欄の上部にある Changes（Open changes）を選択します。変更されたファイルの一覧とコード差分を確認します。


操作位置の例です。画像内の検索機能は、本章の変更内容とは異なります。

  1. ゲームカードの描画を担う src/components/GameCard.astro に、星評価を表示する変更があることを確認します。次のコードは、数値と null を分ける条件の説明例です。既存の StarRating コンポーネントを再利用した実装では、数値側がコンポーネントの呼び出しになることもあります。
{game.starRating !== null ? (
    <span class="text-xs font-medium px-2.5 py-0.5 rounded bg-amber-900/60 text-amber-300" data-testid="game-rating">
        ★ {game.starRating} / 5
    </span>
) : (
    <span class="text-xs font-medium text-slate-500" data-testid="game-rating-empty">
        No rating yet
    </span>
)}

補足 Copilotの出力は毎回同じとは限りません。上記とコードが違っていても、要求を満たしていれば採用できます。ただし、同等の動作になっているかは差分とテストで確認してください。見た目の類似やエージェントの説明だけでは判断できません。

値の意味からレビューする

if (game.starRating) のように値の真偽だけで分けると、JavaScriptでは 0 も偽として扱われます。そのため、0点が未評価と表示される実装になっていないか確認します。このデータ型では null が未評価なので、数値との区別を明示する必要があります。

入力 期待する意味と確認内容
4.2 小数を含む評価を5点満点として表示する
0 0点という評価を表示し、No rating yetにしない
5 上限の評価を表示する
null No rating yetを表示し、数値の評価を表示しない

さらに、既存のタイトルや説明、ゲーム詳細へのリンクが保たれているか確認します。星の形や色だけに意味を任せず、テキストや読み上げ用の名前からも評価値が分かることを確かめましょう。数値表示と No rating yet が同時に出ないこともレビューの対象です。

テストのコードもChangesで読みます。テスト内に条件式だけをコピーして検査しても、実際のGameCardにその実装が使われたことは確認できません。境界値を渡してコンポーネントをレンダリングし、その出力に期待した表示とリンクがあるかを検査する必要があります。不足があれば、同じセッションで次のように追加指示を送ります。

テストがGameCard.astroの実際のレンダリング結果を検査しているか確認してください。
4.2、0、5、nullについて、表示される内容と表示されない内容を確認し、ゲーム詳細へのリンクも検査してください。
通常のCSVやDBは変更せず、テスト用データを使ってください。
不足を修正し、lint、型検査、単体テスト、E2E、buildの結果を報告してください。
PRはまだ作成しないでください。

変更を確認する

生成されたコードを目視で確認するだけでなく、App の Run メニューから開発サーバーを起動し、ブラウザー上で実際の表示を確認します。

補足 .github/github-app.yml が適用されたセッションの Run メニューを使用します。メニューに実行項目が表示されない場合は、演習用コピーの設定内容と適用状態を講師と一緒に確認してください。

通常の21件はすべて数値評価を持つため、通常画面を見るだけでは null の表示を確認できません。通常データの画面確認と、テスト用データを使う境界値の検査を組み合わせて判断します。

開発サーバーの起動と停止手順

  1. セッション上部の Run options から Run development site を選択します。

    • ボタンが Run Run development site と表示されている場合は、クリックして起動します。
    • すでに Stop Run development site と表示されている場合は稼働中ですので、そのまま次の手順へ進んでください。

  1. Runのターミナルに表示されたローカルURLを開きます。Browserパネルが自動で開かない場合は、表示されたURLを別ブラウザーで開いてください。ポート番号は自分の実行結果を使います。
  2. トップページの21件のカードに星評価が表示され、タイトル、説明、詳細へのリンクが保たれていることを確認します。通常画面で出現しない null と境界値は、前節のレンダリングテストの結果で確認します。
  3. 確認後、セッション上部の Stop Run development site を選択します。Runのターミナルで Shell session ended などの終了表示を確認してください。停止後もブラウザーには直前の画面が残る場合があるため、その画面だけで稼働中と判断しないようにします。

ここまでに、差分では変更の範囲、ローカルの画面では利用者に見える結果、テストでは通常画面に現れない条件を確認しました。それぞれ確認できる対象が違うため、どれか1つの成功で他を省略せず、結果を合わせて判断します。

ヒント App内で組み込みターミナルを開く場合は、Toggle panel → +（Add tab）→ Terminal からアクセスできます。開発サーバーの起動・停止には、上記のRunメニューを使います。

最初の pull request を作成してマージする

動作確認が完了したので、コードをリポジトリへ反映します。エージェントに pull request の作成を依頼し、自身でレビューを行ったうえでマージを実施します。本章では手動マージを行いますが、後続レッスンでは自律処理させる方法も体験します。

PRはセッションから作成し、差分やCIの結果をApp内で確認できます。作成済みのPRをサイドバーから開く場合は Pull requests を使います。機能の説明はGitHub公式のPR管理手順も参照してください。

  1. 画面右上にある Create PR を選択します。
  2. ブラウザー認証を求められた場合は、Sign in with your browser を選択し、画面の指示に従って認証します。
  3. Copilot が pull request の作成処理を開始します。
  4. 作成されたPRのリポジトリが自分の演習コピーで、取り込み先が main であることを確認します。本章では Agent mergeをOff にして、手動でマージするところまで進めます。
  5. チャット欄のすぐ上にある PR バブルを選択し、レビューペインで pull request の内容を最終確認します。
  6. Ready to merge を選択し、ダイアログのCI結果を確認します。このボタンの表示だけでは、CI全成功とは判断できません。Checks are running や実行中のジョブがあれば待ち、すべてのジョブの成功を確認します。表示が更新されない場合は画面を開き直し、必要に応じてGitHub Webの同じPRでも照合してください。
  7. 差分、テスト結果、未解決のレビュー指摘を確認したうえで、Merge pull request を選択してmainへマージします。
  8. AppとGitHub Webで対象PRが Merged になったことを確認します。次章では、マージ済みのmainから新しいworktreeを開始します。

CIは、共有された環境で変更を検査する仕組みです。ボタンがマージ可能に見えることと、用意された検査がすべて成功したことは別なので、ジョブの結果まで読みます。これで星評価の変更がリポジトリのmainへ取り込まれました。公開サイトへのデプロイは本章では扱いません。

まとめと次のステップ

最初のエージェントセッションを開始し、レビューした変更をmainへ取り込みました。

  • エージェントセッションを開始し、画面構成と作業ディレクトリの扱いを理解した
  • ゲームカードに小規模で対象を絞った変更を加えるようエージェントへ指示した
  • 差分ビュー（Changes）でコードの変更内容をレビューした
  • アプリをローカル開発サーバーで起動し、ブラウザー上で星評価の表示を確認した
  • pull request を作成し、CI 完了を確認したうえで手動マージを行った

振り返りとして、「0とnullを分ける理由」「通常の21カードを見るだけでは確認できないこと」「Ready to mergeが表示された後に読む情報」を説明してみましょう。追加指示を送った場合は、最初の出力で不足していた確認と、修正後に得られた根拠を振り返ります。次の課題でも、依頼、差分、動作、テストのつながりを追う習慣を使います。

次は、エージェントの一貫したコーディング品質を保つため、リポジトリにカスタム指示（Custom Instructions）の標準ルールを追加します。バックログのIssueを起点として進めましょう。レッスン3「カスタム指示によるCopilotのガイド」へ進んでください。
