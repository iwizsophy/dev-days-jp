3.1 章の概要

前章では、課題一覧とChatsを使いました。この章では実装用のエージェントセッションを開始し、Tailspin Toysに最初の変更を加えます。

ゲームのデータには星評価があり、詳細ページにも表示されています。一方、トップページの一覧カードには評価がありません。既存の値と表示部品を使ってカードにも評価を表示し、利用者が一覧でゲームを選ぶときの情報を増やします。

依頼した内容と生成された差分を比べるには、変更の範囲を絞る方法が有効です。小さな表示の変更でも、0点と未評価の区別、既存リンクの維持など、判断が必要な条件を含みます。依頼、レビュー、動作確認、PRのマージまでを一通り体験しましょう。

3.2 この章で学ぶこと

到達した状態 自分でできること
作業対象と実行場所を確認できる mainを基にした新しいworktreeで編集を始める
小さな変更の仕様と確認条件を伝えられる 星評価と未評価の表示方法、既存のカード構造とリンクを保つ条件を伝える
差分、画面、テストを合わせて判断できる 依頼を満たすか確認し、不足があれば修正を依頼する
CIを読んで手動マージできる レビューした変更を自分のmainへ取り込む

3.3 取り組む前に

前章でAppに接続した演習用コピーを使います。テンプレートの設定を承認し、入力欄へ進めることを確認してください。実装を始めるセッションでは、Node.jsのバージョンも確認します。

本章の作業場所は、mainを基に作る新しいworktreeです。ローカルリポジトリを実行場所に選ぶと、既存の作業フォルダーを使います。編集前にプロジェクト、作業ディレクトリ、ブランチを確かめ、同じcheckoutを使う複数セッションでは同時に編集しないようにします。

3.4 体験すること

実装前に、0点と未評価をどのように表示し分けるか考えてみましょう。生成されたコードを読む際も、次の手順でその予想と結果を比べます。

3.4.1 セッションと環境を確認する

自分の演習用プロジェクトで、新しいセッションを開始してください。作業場所を確認してから変更を依頼します。

  1. GitHub Copilot appを開きます（起動済みの場合はそのまま進めます）。

  2. サイドバーの Projects で、演習用プロジェクトを右クリックし、メニューの + New session を選択します。

  3. New 画面の入力欄下部に、自分の演習用プロジェクト名が表示されていることを確認します。実行場所は New worktree、開始元は main を選びます。モードは、応答を読みながら指示を加える Interactive で進めます。

Interactive・Plan・Autopilotの違いは公式のモード説明で確認できます。

3.4.1.1 実装前の環境確認

ローカルのターミナルとAppのセッションでは、実行するNode.jsが異なる場合があります。これからテストやビルドを行うセッションでの確認は、環境を原因とするエラーかを判断するための手がかりです。

  1. 機能の実装を依頼する前に、次のプロンプトを送信します。
このセッションで node --version を実行し、コマンドの出力をそのまま報告してください。
作業ディレクトリと現在のブランチも確認してください。
ファイル変更、追加インストール、PR作成はしないでください。
  1. ツールの実行結果で、Node.js 24系の24.19.0以降が使われていることを確認します。作業ディレクトリとブランチも、今回のworktreeのものか確かめます。コマンドが見つからない場合や要件を満たさない場合は、前章までのNode.jsの準備を見直します。Node.jsを切り替えた後はAppを再起動し、このセッションで再確認してから実装へ進みます。

エージェントの説明に書かれたバージョンを、ツールのコマンド出力と照合します。環境の確認ができたら、同じセッションで星評価の実装を依頼します。

3.4.2 星評価の実装を依頼する

  1. 次のプロンプトを入力し、変更を依頼します。
ゲームカードに各ゲームの星評価を表示してください。
Game 型には starRating があり、5点満点の数値、または未評価を示す null が入ります。
src/components/GameCard.astro の各カードに表示し、null の場合は「No rating yet」と表示してください。
0は評価値として表示し、未評価と区別してください。
詳細ページの既存の評価表示と関連コンポーネントを確認し、再利用できるものを使ってください。
変更は小さく保ち、カードの構造やゲーム詳細へのリンクは組み替えないでください。
通常データを変更せず、GameCardの実際のレンダリング結果で4.2、0、5、nullの表示とリンク構造をテストしてください。
利用するNode.jsのバージョン、変更内容、実行したテストと結果を報告してください。
PR作成とマージは、後で指示するまで行わないでください。
  1. Enter キーを押して、プロンプトを送信します。

エージェントが行うのは、コードの調査と星評価の表示に必要な変更です。完了報告を受けたら、次の手順で実際の差分とテスト結果を読み、依頼した仕様と照合してください。

3.4.3 差分とテストをレビューする

マージ前に、生成された変更を人がレビューします。Changesで対象ファイルと差分を読み、星評価を加えるために何が変わったか確かめましょう。

  1. 会話入力欄の上部にある Changes（Open changes）を選択します。変更されたファイルの一覧とコード差分を確認します。

  1. ゲームカードの描画を担う src/components/GameCard.astro に、星評価を表示する変更があることを確認します。

3.4.3.1 値の意味からレビューする

if (game.starRating) のように値の真偽だけで分けると、JavaScriptでは 0 も偽として扱われます。そのため、0点が未評価と表示される実装になっていないか確認します。このデータ型ではnullが未評価です。数値との区別を明示してください。

入力 期待する意味と確認内容
4.2 小数を含む評価を5点満点として表示する
0 0点という評価を表示し、No rating yetにしない
5 上限の評価を表示する
null No rating yetを表示し、数値の評価を表示しない

さらに、既存のタイトルや説明、ゲーム詳細へのリンクが保たれているか確認します。星の形や色だけに意味を任せず、テキストや読み上げ用の名前からも評価値が分かることを確かめましょう。数値表示と No rating yet が同時に出ないこともレビューの対象です。

テストのコードもChangesで読みます。テスト内に条件式だけをコピーして検査しても、実際のGameCardにその実装が使われたことは確認できません。境界値を渡してコンポーネントをレンダリングし、その出力に期待した表示とリンクがあるかを検査する必要があります。不足があれば、同じセッションで次のように追加指示を送ります。

テストがGameCard.astroの実際のレンダリング結果を検査しているか確認してください。
4.2、0、5、nullについて、表示される内容と表示されない内容を確認し、ゲーム詳細へのリンクも検査してください。
通常のCSVやDBは変更せず、テスト用データを使ってください。
不足を修正し、lint、型検査、単体テスト、E2E、buildの結果を報告してください。
PRはまだ作成しないでください。

3.4.4 ブラウザーで動作を確認する

AppのRunメニューから開発サーバーを起動し、ブラウザーで実際の表示を確認してください。ここでは利用者に見える結果を、依頼した仕様と比べます。

補足 .github/github-app.yml が適用されたセッションのRunメニューを使用します。メニューに実行項目が表示されない場合は、演習用コピーの設定内容と適用状態を講師と一緒に確認してください。

通常の21件はすべて数値評価を持つため、通常画面だけではnullの表示を確認できません。実際の画面と、テスト用データによる境界値の検査を合わせて判断します。

3.4.4.1 開発サーバーの起動と停止手順

  1. セッション上部の Run options から Run development site を選択します。

    • ボタンが Run Run development site と表示されている場合は、クリックして起動します。
    • すでに Stop Run development site と表示されている場合は稼働中ですので、そのまま次の手順へ進んでください。

  1. Runのターミナルに表示されたローカルURLを開きます。Browserパネルが自動で開かない場合は、表示されたURLを別ブラウザーで開いてください。ポート番号は自分の実行結果を使います。
  2. トップページの21件のカードに星評価が表示され、タイトル、説明、詳細へのリンクが保たれていることを確認します。通常画面で出現しない null と境界値は、前節のレンダリングテストの結果で確認します。
  3. 任意のカードから詳細ページへ移動し、評価値が一覧と一致することを確認します。一覧へ戻れることも確かめてください。
  4. 確認後、セッション上部の Stop Run development site を選択します。Runのターミナルで Shell session ended などの終了表示を確認してください。停止後もブラウザーには直前の画面が残る場合があるため、その画面だけで稼働中と判断しないようにします。

3.4.5 最初のPull Requestを作成してマージする

動作確認を終えた変更を、PRでmainへ取り込みます。この章で使うのは手動マージです。後の章では、同じ確認を経てエージェントにマージを任せる方法も体験します。

PRはセッションから作成し、差分やCIの結果をApp内で確認できます。作成済みのPRをサイドバーから開く入口はPull requestsです。機能の説明はGitHub公式のPR管理手順も参照してください。

  1. 画面右上にある Create PR を選択します。
  2. ブラウザー認証を求められた場合は、Sign in with your browser を選択し、画面の指示に従って認証します。
  3. Copilotがpull requestの作成処理を開始します。
  4. 作成されたPRのリポジトリが自分の演習コピーで、取り込み先が main であることを確認します。本章では Agent mergeをOff にして、手動でマージするところまで進めます。
  5. チャット欄のすぐ上にある PR バブルを選択し、レビューペインでpull requestの内容を最終確認します。
  6. Ready to merge を選択し、ダイアログのCI結果を確認します。このボタンの表示だけでは、CI全成功とは判断できません。Checks are running や実行中のジョブがあれば待ち、すべてのジョブの成功を確認します。表示が更新されない場合は画面を開き直し、必要に応じてGitHub Webの同じPRでも照合してください。

  1. 差分、テスト結果、未解決のレビュー指摘を確認したうえで、Merge pull request を選択してmainへマージします。
  2. AppとGitHub Webで対象PRが Merged になったことを確認します。次章では、マージ済みのmainから新しいworktreeを開始します。

これで星評価の変更がリポジトリのmainへ取り込まれました。公開サイトへのデプロイは本章では扱いません。

3.5 結果の整理と振り返り

星評価の表示を依頼し、レビューした変更を自分のmainへ取り込みました。確認したことを整理しましょう。

確認した根拠 判断したこと
作業ディレクトリとブランチ 今回のworktreeで編集していること
Changes 既存表示とリンクを保ち、星評価だけを加えていること
通常データの画面 利用者が一覧で評価を読め、詳細ページへ移動できること
レンダリングテスト 4.2、0、5、nullを仕様に沿って表示し分けること
PRのCIとMerged 用意された検査に成功し、変更をmainへ取り込んだこと

「0とnullを分ける理由」「通常の21カードだけでは確認できないこと」「Ready to mergeの表示後に読む情報」を、自分の言葉で説明してみましょう。

最初に予想した表示と、生成された実装は一致しましたか。追加指示を送った場合は、何が不足し、修正後にどの根拠を得られたかを振り返ります。次の課題でも、依頼、差分、画面、テストのつながりを追います。

次章の題材は、エージェントとコードの書き方を共有するカスタム指示です。第4章「カスタム指示によるCopilotのガイド」へ進んでください。

3.6 補足

3.6.1 小さな変更から始める理由

Tailspin Toysの各ゲームには星評価のデータが保持されており、ゲーム詳細ページにはすでに表示されています。一方、ホームページの一覧カードにはタイトル、カテゴリー、パブリッシャー、説明文のみが表示されており、星評価は含まれていません。

一覧カードにも既存の星評価を表示する課題は、対象を絞って取り組めます。データを増やす変更と表示の変更を分けられるため、初めての共同作業でも差分を追いやすくなります。

この課題で行うのは、すでにある値を一覧にも表示する変更です。データを新しく集めたり、保存方法を変えたりする必要はありません。画面上の変更が小さいほど、依頼した範囲と生成された差分を比べやすくなります。同時に、「値が0」と「まだ評価がない」の違いのように、小さな表示にも仕様の判断が含まれることを学びます。

3.6.2 セッションとworktreeの役割

セッションとは、特定のプロジェクトを対象としてエージェントと対話を行う作業空間です。サイドバーのプロジェクト一覧から起動できます。

GitHub公式のセッション手順では、新しいworktree、ローカルリポジトリ、クラウドの実行環境を選べます。本章で選ぶ実行場所はNew worktreeです。mainを基にした別の作業場所で変更します。worktreeを分けることは作業中のファイルを分けるためであり、変更が自動的にmainへ反映されるという意味ではありません。レビューとPRのマージを経て、次章で利用できる状態にします。

各セッションでは、会話、操作履歴、差分を合わせて読みます。

要素 確認する内容
Chat エージェントへの指示と回答
Tool Activity 調査や編集、検査で実行された操作
Changes 変更ファイルとコードの差分

ヒント App内で組み込みターミナルを開く場合は、Toggle panel → +（Add tab）→ Terminal からアクセスできます。開発サーバーの起動・停止には、上記のRunメニューを使います。

3.6.3 依頼に含める仕様と確認方法

補足 プロンプトでは更新対象ファイルと期待する表示を指定しています。ファイル指定は必須ではありませんが、変更範囲を共有すると、レビュー時にも目的に沿った変更か確かめやすくなります。既存実装の調査を依頼しているのは、同じ評価表示を別々に作り、一覧と詳細で表示が食い違うことを避けるためです。

今回の依頼に含めるのは、「何を表示するか」「既存の何を保つか」「どう確かめるか」の三つです。たとえば、星が見えるだけでは null の扱いやリンクの維持までは分かりません。実装前に受け入れ条件を具体化しておくと、完了報告を読んだ後に確認する対象も明確になります。

3.6.4 0とnullを区別するコードの読み方

次のコードは、数値と null を分ける条件の説明例です。既存の StarRating コンポーネントを再利用した実装では、数値側がコンポーネントの呼び出しになることもあります。

{game.starRating !== null ? (
    <span class="text-xs font-medium px-2.5 py-0.5 rounded bg-amber-900/60 text-amber-300" data-testid="game-rating">
        ★ {game.starRating} / 5
    </span>
) : (
    <span class="text-xs font-medium text-slate-500" data-testid="game-rating-empty">
        No rating yet
    </span>
)}

補足 Copilotの出力は毎回同じとは限りません。上記とコードが違っていても、要求を満たしていれば採用できます。ただし、同等の動作になっているかは差分とテストで確認してください。見た目の類似やエージェントの説明だけでは判断できません。

3.6.5 差分、画面、テスト、CIで確かめること

ここまでに、差分では変更の範囲、ローカルの画面では利用者に見える結果、テストでは通常画面に現れない条件を確認しました。それぞれ確認できる対象が違うため、どれか1つの成功で他を省略せず、結果を合わせて判断します。

CIは、共有された環境で変更を検査する仕組みです。ボタンがマージ可能に見えることと、用意された検査がすべて成功したことは別なので、ジョブの結果まで読みます。
