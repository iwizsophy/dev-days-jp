この章の進め方 Appをインストールして演習用リポジトリを接続します。課題一覧と設定を確認し、クイックチャットで相談と実装の使い分けを学びます。

操作の背景や考え方は、章末の補足にまとめています。

Node.js の準備と演習用リポジトリの作成が完了したため、本レッスンではアプリをインストールし、リポジトリを接続してワークスペースの構造を確認します。

本レッスンでの到達目標は次の4点です。

  • GitHub Copilot app をインストールし、GitHub アカウントでサインインする。
  • GitHub リポジトリから演習プロジェクトをアプリに追加する。
  • テンプレートによって自動生成されたバックログ Issue を含め、ワークスペースの各領域を確認する。
  • クイックチャットを試し、アプリ自体の仕組みについて質問する。

1.1 GitHub Copilot app をインストールして構成する

補足 本教材では、有効なCopilotプランを持つGitHubアカウントでサインインします。公式ドキュメントでは全Copilotプランが対象です。演習の完走に必要な利用枠は事前に確認してください。Copilot BusinessまたはCopilot Enterpriseの組織では、CLI用とは別の GitHub Copilot app ポリシーが有効である必要があります。利用条件は公式の概要、Gitのインストールなどの前提は公式の開始手順で確認できます。

Windows、macOS、Linux 向けにインストーラーが提供されています。アプリを導入・認証し、演習用リポジトリを追加します。

最新版のAppを使用します。すでにインストールしている場合は、更新してから演習を始めてください。

  1. ブラウザーで GitHub Copilot app のダウンロードページ を開きます。
  2. 使用している OS 向けの最新版のインストーラーをダウンロードし、画面の指示に従ってインストールします。
  3. インストール完了後、Copilot app を起動します。
  4. Sign in to GitHub を選択し、ブラウザーが開いたら認証を完了させます。
  5. 認証完了後にリポジトリの接続画面（Connect your repositories）が表示されたら、ここでは選択せずに進みます。本教材では、初期設定の完了後にサイドバーから演習用リポジトリを追加します。
  6. Continue を選択して進みます。
  7. テーマ（外観）の選択画面が表示されたら、好みのテーマを選んで Finish を押します。

1.2 プロジェクト接続とリポジトリ設定の確認

初期設定完了後のプロジェクト追加入口は、サイドバーの Projects 横にある +（New project or session）です。ここから Add GitHub repository、Clone repository、および Open folder を選択できます。

本教材では、GitHub上のIssueやPRと連携した作業を体験するため、次の経路で接続します。Appの利用アカウントと、前章で作成したコピーの所有者を確認してから進めてください。

Repository trustでの承認は、リポジトリ内の設定や拡張を新しいセッションで利用する判断です。ボタンを押す前に内容を読む習慣をつけましょう。後の章で設定を変更した際にも、変更された内容を確認して承認します。

  1. Projectsの + → Add GitHub repository を選び、前章で控えた自分の owner/repo を検索して追加します。
  2. Review repository content が表示されたら、設定や拡張の内容を開いて確認します。テンプレートには、後の演習で使う起動コマンドやMCPなどの設定が含まれています。
  3. Repository trust で対象が自分の演習コピーであることと、承認する内容を確認し、Accept for new sessions を選択します。
  4. 入力欄へ進めたことを確認します。実装用の新規worktreeは次章で選び、準備中の表示がある場合は完了を待ちます。

補足 接続後に入力欄が表示されない場合や、GitHubの連携エラーが出る場合は、対象リポジトリ、設定の承認状態、サインインしたアカウントを講師と確認してください。設定画面を通過したことと、アプリのビルド・テストが成功したことは別です。実装を始めた後は、それぞれの結果も確認します。

1.3 バックログ Issue の確認

GitHubと連携すると、Appで演習用リポジトリの課題を確認できます。まず自分のプロジェクトを選び、確認する課題の範囲を決めます。Issueには変更の背景と受け入れ条件が記載されているので、後の実装を依頼する前に読んでおきましょう。

  1. サイドバーの Projects で、自分の演習用プロジェクト（例：dev-days-tailspin-toys）を選択します。
  2. プロジェクトの一覧画面で Issues フィルターを選択します。
  3. 表示条件を確認し、未割り当ての課題も含めてOpen Issueを表示します。自動生成された課題は未割り当てなので、Assigned to me（自分に割り当てられた課題）のビューでは表示されません。Nothing here と表示される場合は、タブ右の + → New view を選択し、State: Open、追加の検索条件なしで Save します。

  4. テンプレート作成時に自動生成された8件のバックログIssueが表示されていることを確認します。本ワークショップでは、特に次の3件を使います。

    • Allow users to filter games by category and publisher（フィルター機能の実装）
    • Update our repository coding standards（コーディング規約・ドキュメント標準の追加）
    • Add a search box to find games by title（タイトル検索の実装）

  5. 任意のIssueを選択し、背景と受け入れ条件を読みます。各Issueは、後続のレッスンでエージェントセッションを開始する起点となります。この章では内容の確認までに留め、実装は後の章で始めます。

補足 リポジトリ自体が見つからない場合は、Add GitHub repositoryから自分のコピーを追加したか確認します。リポジトリは選べるのに課題が見えない場合は、割り当てやStateの絞り込み条件を確認してください。GitHub Webにも課題がない場合は、前章のBootstrap template issuesの実行状況を調べます。

1.4 クイックチャット（Quick Chat）を試す

Chatsは、ブランチやworktreeを作らずに質問やアイデア出しをする場所です。履歴は保存され、後から回答を読み返せます。Interactiveは、エージェントとの進め方を表すモードです。相談する場と進め方の違いを、GitHub公式のセッション説明でも確認できます。ここでは、アプリの仕組みについて質問してみましょう。

  1. サイドバーの Chats を右クリックします。

  2. メニューから New chat を選択します。入力欄の下で対象が Chat、モードが Interactive であることを確認します。

  3. プロンプト入力欄に次のテキストを入力し、送信します。

    GitHub Copilot app は worktree をどのように使いますか？
日本語で簡潔に説明してください。説明だけを行い、ファイル変更、
リポジトリ操作、コマンド実行はしないでください。

  4. 送信後、会話ビューに日本語での解説が返答され、処理完了後にステータスが Idle に戻ることを確認します（※この回答はエージェント自身による解説であり、worktree の実動作の証明ではありません。実際の実装セッションにおける worktree 分離は次章以降で確認します）。

1.5 完了の確認

GitHub Copilot app をインストールし、プロジェクトを接続してワークスペースを確認しました。

  • アプリをインストールして GitHub アカウントでサインインした
  • GitHub リポジトリから演習プロジェクトを追加した
  • ワークスペースの構造を確認し、Issues で用意されたバックログIssueを確認した
  • クイックチャットを使って、その場限りの質問を試した

1.6 補足

1.6.1 Appとworktreeの役割

開発チームは、増え続けるバックログを効率的に消化するため AI エージェントの導入を進めています。Copilot app を利用することで、Issue の選定、エージェントへの実装指示、変更差分のレビュー、Pull Request の作成とマージまでを一元的に管理できます。本レッスンでは、アプリのセットアップを行い、プロジェクトについての対話を開始できる状態を整えます。

GitHub Copilot appは、エージェント主導の開発に特化したデスクトップアプリケーションです。GitHub Copilot CLIを基盤とし、GitHubのリポジトリ、ブランチ、CIパイプラインと連携します。複数のエージェントに作業を分担させ、開発者は指示とレビューを進められます。この位置づけはGitHub公式の概要でも説明されています。

実装セッションでは、新しいworktreeなどの実行場所を選びます。worktreeは、同じリポジトリの別ブランチを別の作業フォルダーで扱う仕組みです。星評価とフィルターを別々に試すような場合に、作業中のファイルを分けられます。ただし、別のworktreeで完了した変更を利用するには、マージ後の状態を次の作業へ引き継ぐ必要があります。本教材では各章でマージの結果を確かめてから次の機能へ進みます。実行場所の選択肢は公式のセッション開始手順を参照してください。

1.6.2 ワークスペースと課題一覧の見方

プロジェクトを接続したら、アプリの主要な作業領域を確認します。サイドバーの項目と、プロジェクトを選択した後に使う一覧を確認しましょう。

  • Projects：プロジェクトとエージェントセッションを管理する領域。実装用セッションと独立したworktreeは次章以降で使います。
  • Chats：リポジトリの作業ツリーやブランチを作成せず、単発の質問や相談を行える会話領域。
  • Issues / Pull requests：GitHubの課題とPRを確認する一覧。演習用プロジェクトを選び、Issuesで課題の検索やセッション開始、Pull requestsで差分やCI結果の確認を行います。
  • Automations：スケジュールや手動操作で実行する、保存済みのエージェント自動化タスクを管理する領域（演習8で作成します）。
  • Customize：MCP サーバー、Plugins、Skills、Extensions、Canvas、および Installed の各設定・管理画面を開く入口。

この章では、相談する場所、実装する場所、GitHub上の課題や成果を確認する場所の違いをつかみます。たとえば、実装前の質問はChats、星評価の編集はProjectsのセッション、取り込む前の確認はPull requestsを使います。各機能の役割はGitHub公式のIssue・PR管理手順でも確認できます。

「一覧に何もない」だけでは、課題の生成失敗とは判断できません。対象リポジトリ、表示条件、GitHub Web上の実データを順に照合すると、接続と表示のどちらを確認すべきか判断できます。

1.6.3 チャット一覧のコンテキストメニュー確認

完了したチャット項目を Chats一覧で右クリック し、表示される操作を確認します。名前の変更やアーカイブなど、会話を整理する項目の役割を読んでみましょう。この演習ではメニューの確認までとし、共有や削除は行いません。

1.6.4 振り返り

振り返りとして、Chatsでの相談と実装セッションの違い、Assigned to meが空だった理由を説明してみましょう。設定承認では何を確認したかも振り返ると、次章で作業対象や権限を自分で確かめながら進められます。
