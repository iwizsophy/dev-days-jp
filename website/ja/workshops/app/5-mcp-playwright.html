この章の進め方： テンプレートのMCP設定を確認し、前章のセッションからPlaywrightでブラウザーを操作します。フィルターの結果とキーボード操作を確かめ、ブラウザーやサーバーの終了まで確認してください。設定画面が見つからない場合は、講師に相談してください。

前章では、プロジェクトに組み込まれた自動テストスイート（単体テストやE2Eテスト）を用いてフィルター機能を実装・検証しました。自動テストに加えて、エージェントが実際のブラウザーを対話的に操作し、その結果を読み取れるようにすると、テストにまだ書いていない操作順序や表示状態も調べられます。操作できない要素や期待と違う結果があれば、その場で原因を調べ、修正と再確認へ進めます。

本レッスンでは、Model Context Protocol (MCP) を通じて AI エージェントに外部ツールの操作能力を付与する仕組みを学び、Copilot がローカル開発サーバー上の Web サイトを直接操作できるように Playwright MCP server を連携させます。

このレッスンでは、次の内容を学習します。

  • Model Context Protocol (MCP) の概念と、GitHub Copilot app における活用方法を理解する
  • アプリでPlaywright MCP serverの既存設定を確認し、必要な場合に追加・有効化する
  • エージェントに実際のブラウザーを操作させ、フィルター機能の挙動を手動テストさせる

シナリオ

単体テストやスクリプト化されたエンドツーエンドテストに加えて、開発中のUIをユーザーの操作に沿って検証します。エージェントへブラウザーの操作手段を与え、選択欄やボタンを操作したときに、新機能が仕様どおりに動くかを確かめます。

この章では、エージェントへ操作を依頼し、返ってきた観察結果から次の確認を決める探索的な検証を行います。一方、前章のE2Eテストには、決めた操作と期待結果を保存して繰り返し検査する役割があります。MCPで一度成功した操作が、そのままテストコードとして残るわけではありません。新しい不具合を見つけて修正したら、今後も確認すべき条件をE2Eテストへ追加するか検討します。

Model Context Protocol (MCP) とは

Model Context Protocol (MCP)は、AIエージェントが外部のツールやサービスと情報をやり取りするためのオープンなプロトコルです。MCPを導入すると、エージェントは外部システムと対話し、リソース（resources）を通じて情報を取得したり、ツール（tools）を通じてユーザーに代わる操作を実行したりできます。実際に利用できる情報や操作は、接続先と付与された権限によって決まります。

エージェントは、個別の外部サービスとの橋渡しを担う MCP server を経由してこれらのツールやリソースにアクセスします。MCP server はローカルで動作するプロセス（CLI ツールや NPM パッケージ）やリモート API とエージェント間の通信を仲介します。各 MCP server は、エージェントが利用可能な固有のツールセットとリソース群を提供します。

代表的な MCP server には次のようなものがあります。

  • GitHub MCP Server：GitHub の各種 API にアクセスするツール群を提供します。エージェント自身によるリポジトリの作成・更新、Issue や pull request の管理などが可能になります。
  • Playwright MCP Server：Playwright を用いたヘッドレス／有頭ブラウザーの自動操作機能を提供します。エージェント自身がページ遷移、フォーム入力、ボタンのクリック、DOM スナップショットの取得などを実行できます。

GitHub は、コミュニティによる発見と貢献を促進するため MCP registry をホストしており、多種多様な MCP server が公開されています。

本演習で接続するPlaywright MCPは、主に構造化されたアクセシビリティスナップショットを使ってページを読み取ります。ボタンの名前や役割、選択状態などを調べ、クリックやキー入力のツールを呼び出します。Microsoftの公式READMEにこの動作が説明されています。画面のピクセルを見てすべての見た目を判定する仕組みではないため、色や配置などの見た目は、必要に応じてスクリーンショットや人間の画面確認でも確かめます。

注意 MCP server は、プロジェクトに導入する外部ライブラリや依存関係と同様に慎重に取り扱う必要があります。導入前にソースコードや発行元を精査し、セキュリティ上の影響を評価してください。信頼できる MCP server のみを利用し、機密情報や特権的な操作へのアクセス権限を安易に付与しないよう注意してください。

Playwright MCP server の接続を確認する

Appの公式ドキュメントでは、リポジトリやCopilot CLIに設定したMCP serverをAppでも利用できると説明されています。まず既存設定を確認し、未登録の場合にカタログから追加します。

リポジトリ側に MCP 定義が存在する場合：
本教材のテンプレートには、すでに .mcp.json 内の mcpServers フィールドに Playwright 等が定義されています。GitHub 連携プロジェクトを右クリック → Settings → MCP servers から確認できます。 画面に Trust repository が表示された場合は、定義内容を確認のうえで利用者が信頼を承認してください（これは Repository configuration の Trusted 表示とは別の承認です）。二重登録を避けるため、既存の定義状態を確認したうえで以下の手順を参照してください。

.mcp.jsonにあるgithub、playwright、astro-docsの接続状態を確認します。既存のplaywrightがConnectedなら、同じサーバーをもう一つ追加する必要はありません。定義を見ると、playwrightはnpxでローカルプロセスを起動し、他の2つはHTTPのURLへ接続する構成です。実行するコマンドや接続先を読むことも、設定を信頼する判断の一部です。

設定画面のConnectedは接続状態の確認です。演習を進められるかは、フィルターのセッションから実際にPlaywrightのツールを呼び、結果が返るかで確かめます。たとえばタブ一覧の取得は呼び出し確認になりますが、フィルターが正しく動くことはまだ確認していません。次のブラウザー検証まで進めて、接続と機能の結果を別々に確認してください。

既存設定が正しく読み込まれない場合の対処

No MCP servers loadedと表示される場合は、リポジトリの信頼状態と.mcp.jsonの形式を確認してください。公式のリポジトリ別設定形式では、定義をmcpServersフィールドに記述します。serversなど別のキーになっている場合は修正が必要ですが、教材テンプレートはこの形式になっているため、通常は編集不要です。

設定を修正した場合は、AppのSettings画面でRefreshを選択し、接続状態を確認します。上記の公式リンクは設定ファイル形式の参照先です。CLI用の設定コマンドと、Appの画面上の操作を混同しないようにしてください。

セッション再起動（/restart-session）の活用

信頼状態と接続設定を確認しても、開いているセッションからPlaywrightのツールを呼び出せない場合は、会話入力欄から/restart-sessionを送信して再接続を試せます。App公式のスラッシュコマンド一覧では、履歴を保持して現在のセッションを再起動するコマンドと説明されています。ツールを呼び出せている場合、この操作は不要です。

GUI からの新規登録手順

リポジトリ定義がなく、アプリのGUIから手動登録する場合の手順は次の通りです。教材テンプレートの既存定義でConnectedとなった場合は、この登録を飛ばして次節へ進みます。App公式の手順も、CustomizeからMCPを探し、Installedで登録済みの設定を管理する流れを説明しています。

  1. サイドバーの Customize を開きます。
  2. Installed タブの MCP Servers で既存の登録一覧を確認します。すでに登録済みの場合は重複して追加しないよう注意してください。
  3. 未登録の場合は MCP タブを開き、Playwrightを探します。Featuredセクションに見つからなければ、Search MCP serversから検索してください。
  4. Playwright カードを選択して登録フォームを開きます。ローカルで起動する設定例は、Server name が playwright、Type が Local、Command が npx、Arguments が -y @playwright/mcp@latest です。
  5. 入力内容を確認し、Add server をクリックして保存します。Installedの一覧に追加されたことを確認してください。
  6. チャットやセッションから実際のツール呼び出しを確かめます。たとえばPlaywrightのbrowser_tabsでタブ一覧を取得するよう依頼し、結果が返るかを確認します。応答にabout:blankが含まれていても、それは開いているタブの状態です。フィルター機能の確認は次節で行います。

補足 サイドバーは左上のトグルボタンまたはCtrl+Bで開閉できます。CustomizeやMCPのメニュー項目が見当たらない場合は、Appのバージョン、組織ポリシーによる制限、および現在の画面状態を記録し、講師と一緒に確認してください。

Playwright で機能を確認するよう Copilot に依頼する

前章から開いたままにしているフィルター機能の実装セッションに戻り、Playwright MCP server を使って新機能の動作を手動検証するよう Copilot に指示します。

  1. 会話入力欄に次のプロンプトを入力して送信します。
このセッションで実装したフィルター機能を、Playwright MCP serverで検証してください。今回のworktreeから開発サーバーを起動し、接続したURLを報告してください。
Issueと承認済みの計画を使い、カテゴリの複数選択、出版社との組み合わせ、解除、キーボード操作を確認してください。通常データと、前章で用意した隔離テストデータによる0件表示を分け、操作・期待結果・実際の結果を報告してください。
検証後はbrowser_closeでブラウザーを閉じ、今回起動したサーバーを停止してください。今回作成した一時DBとMCP出力だけを片付け、テスト用CSV・テストコードや既存の成果物は残してください。実施できなかった項目も明記してください。PR作成・マージは次章まで待ってください。
  1. Copilot は Playwright MCP server を通じてブラウザーを自律起動し、検証ステップを順次実行して結果を会話欄に報告します。タスク実行中、環境によってはデスクトップ上で実際にブラウザーウィンドウが開き、自動操作される様子が視覚的に確認できます。
  2. 報告された概要を Issue の受け入れ条件と照らし合わせてレビューします。もし挙動に問題があれば、pull request を作成する前に追加の指示を出してコードを修正させてください。

「問題ありませんでした」という概要だけでは、何を確認したか判断できません。どのカテゴリと出版社を選び、何件・どのゲームが表示されたか、どのキーで解除したかを確認します。ツール呼び出しと結果も開き、実際の操作から得た報告かを読み取ってください。コードを直した場合は、影響する自動テストとブラウザー操作を再確認します。

  1. 【重要】次のレッスンで Agent Merge を実施するため、このセッションは開いたままにしておきます。

操作結果をレビューする観点

ツールの履歴から、ページへの移動、選択欄やボタンの操作、キー入力といった流れを読み取ります。利用するツールの名前や順序を揃えることより、必要な操作と観察結果が得られることを確認します。

教材の通常データで確認する操作と期待結果は、次の通りです。

操作 期待結果 確認する意味
初期表示 21件 通常データの一覧を表示している
Strategyを選択 4件 一つのカテゴリで絞れる
Puzzleも追加選択 8件 カテゴリ同士のOR条件で、両カテゴリが含まれる
GitHub Gamesも選択 2件 カテゴリと出版社のAND条件で絞れる
Clear filtersで解除 21件 選択状態と一覧が初期状態へ戻る
カテゴリ未選択でGitHub Gamesを選択 5件 出版社だけでも絞れる
カテゴリ未選択でCodeForge Studiosを選択 6件 出版社名を変えた結果を区別できる

通常データが同じでも、選択した出版社が異なれば期待件数は変わります。「出版社単独6件」のように名前を省かず、選択値と件数を一緒に記録してください。

キーボード操作では、カテゴリをSpaceで変更できるか、現在の選択状態が分かるかも確認します。PublisherからTabを使ってClear filtersへ移り、Enterで解除して21件へ戻る操作も試してください。クリックで解除できることだけでは、キーボードでボタンへ到達して操作できることの確認にはなりません。

該当 0 件表示の検証について

通常データセットには全カテゴリーと全パブリッシャーの組み合わせに必ず該当ゲームが存在するため、通常の絞り込み操作のみでは「該当件数 0 件」の画面を再現できません。

前章で用意した3件の専用CSVと隔離SQLiteを使い、通常環境とは別ポートのサーバーで検証します。まずテスト用の3件を表示し、PuzzleとNova Interactiveを組み合わせると0件となることを確認します。0件の説明と結果通知を読み、Clear filtersでテスト用の3件へ戻ることまで確かめます。通常環境へ戻ったときの21件と、隔離環境で解除した後の3件を混同しないでください。

0件表示のために通常のdb/games.csvを変更しないでください。報告にデータの種類、接続URL、初期件数、選択した条件、解除後の件数があれば、別の環境を検査していないかを見分けやすくなります。

検証を終えたときの確認

ブラウザーを閉じても、開発サーバーや一時DBが残っている場合があります。次回のテストが古いサーバーへ接続しないよう、今回起動したものを終了させます。browser_close、サーバー停止、一時DBとMCP出力の削除を確認し、今回使ったポートに待受が残っていないことも照合してください。テストを再実行するためのCSVやテストコードは成果物なので、片付ける一時ファイルと区別します。

これで、エージェント自身が実際のブラウザーをユーザーと同じように操作し、UI 機能の正常性を確認できました。

まとめと次のステップ

GitHub Copilot app から Playwright MCP server を呼び出し、実際のブラウザー操作を通じて新機能の動的検証を実施しました。本章で実施した主な内容は次の通りです。

  • Model Context Protocol (MCP) の基本構造と、アプリに外部ツール（tools / resources）を連携させる仕組みを理解した
  • 既存のPlaywright MCP serverの設定と信頼状態を確認し、セッションから実際にツールを呼び出した。必要な場合の追加登録・再接続方法も確認した
  • エージェントにブラウザーを自律操作させ、フィルター機能の絞り込み、複合条件、キーボード操作、解除、および0件表示を検証した

機能の構築とブラウザー検証が無事に完了しました。次は、Agent Merge を活用し、pull request の作成、CI 監視、競合解決、およびマージまでの一連のリリース作業をエージェントに自律実行させます。レッスン 6「Agent Merge によるマージ」 へ進んでください。

次へ進む前に、MCPで初めて気づいた点と、既存のE2Eテストでも確認していた点を比べてみてください。今回確認した操作・結果・残る未確認項目を整理すると、次章でPRをレビューする根拠として使えます。
