> **この章の進め方：** App で操作します。掲載画像には確認日・バージョン・操作例の対象を添えています。撮影範囲全体を残しているため、会話欄と操作パネルの位置関係を合わせて確認できます。ボタンや機能が見つからない場合は [UI が異なるときの確認](../material/ui-check.md)に沿って講師と確認してください。

前のレッスンでは、ワークスペースの確認とクイックチャットの利用を行いました。本章では、いよいよ**エージェントセッション**を開始し、プロジェクトに最初の変更を加えます。

今回の変更は小規模なものに留めます。ゲームのデータ構造にはすでに星評価が含まれていますが、ホームページのゲームカードにはまだ表示されていません。そこでエージェントにカードへの評価表示を依頼し、生成された変更をレビューしたうえで、最初の pull request としてマージする一連の流れを体験します。

このレッスンでは、次の内容を学習します。

- エージェントセッションを開始し、その構成要素を理解する
- プロジェクトに対し、小規模で対象を絞った変更を加えるようエージェントへ依頼する
- ワークスペースの差分ビュー（Changes）で変更内容をレビューする
- アプリをローカルで実行し、ブラウザー上で変更結果を確認する
- 最初の pull request を作成してマージする

## シナリオ

Tailspin Toys の各ゲームには星評価のデータが保持されており、ゲーム詳細ページにはすでに表示されています。一方、ホームページの一覧カードにはタイトル、カテゴリー、パブリッシャー、説明文のみが表示されており、星評価は含まれていません。

そこで、最初のエージェントセッションの準備運動として、ホームページの各カードにも既存の星評価を表示するようエージェントに依頼します。対象が絞られており自己完結しているため、エージェントとの最初の共同作業として最適な課題です。

## セッションの構造

**セッション**とは、特定のプロジェクトを対象としてエージェントと対話を行う作業空間です。セッションはリポジトリごとにサイドバーに一覧表示されます。

ただし、エージェントが作業を行うディレクトリ環境については、プロジェクトの追加方法やセッションの設定に応じた確認が不可欠です。2026年9月13日の Windows App 1.1.20 実機検証では、**Open folder** で追加したプロジェクトの読み取りセッションは既存の checkout を直接使用しており、専用の worktree は作成されませんでした。すべてのセッションが自動的に独立した環境に分離されるとは見なさず、コードの編集を開始する前に作業ディレクトリと現在のブランチを必ず確認してください。また、同一の checkout を共有する複数セッションで同時に編集を行わないように注意が必要です。

各セッションの画面内は、主に次の3つの要素で構成されています。

1. **会話（Chat）**：エージェントに対する指示や対話のログ
2. **ツールアクティビティ（Tool Activity）**：ファイルの調査や編集時にエージェントが実行した操作の履歴
3. **変更済みファイル（Changes）**：差分（diff）付きで確認できる変更ファイルの一覧

## セッションを開始して変更を依頼する

新しいセッションを開始し、プロジェクトの調査と機能の実装を進めましょう。[前のレッスン][prior-lesson]で GitHub リポジトリから追加した演習用プロジェクトを選択し、変更を依頼します。

1. GitHub Copilot app を開きます（すでに開いている場合はそのまま進めます）。
2. サイドバーの **Projects** で、演習用プロジェクトの横にある **+**（New session in …）を選択します（Windows App 1.1.20 でこの操作導線を確認済みです）。
3. **New** 画面の入力欄下部に、自分の演習用プロジェクト名が表示されていることを確認します（表示される名前自体は各自のリポジトリ名で構いません）。

   ![App の New 画面全体。入力欄と下部のプロジェクト、New worktree、main](../../_images/app-1.1.20-20260913-new-session.png)

4. 次のプロンプトを入力し、変更を依頼します。

   ```plaintext
   ゲームカードに各ゲームの星評価を表示してください。Game 型には starRating があり、5点満点の数値、または未評価を示す null が入ります。src/components/GameCard.astro の各カードに表示し、null の場合は「No rating yet」と表示してください。変更は小さく保ち、カードの構造は組み替えないでください。
   ```

> [!NOTE]
> プロンプト内で、更新対象となるファイル名（`src/components/GameCard.astro`）をあらかじめ指定している点に注目してください。作業対象のファイルを必ず指定しなければならないわけではありませんが、エージェントにあらかじめ方向性を示すことで、意図通りのコードをすばやく生成させ、トークン消費量を抑えることができます。

5. <kbd>Enter</kbd> キーを押して、プロンプトを送信します。

Copilot app がセッションを開始したら、実際の作業場所とブランチを確認します。既存の checkout を直接使用している場合は、今回の変更用ブランチ上にあることを確認してください。エージェントはコードベースを調査し、星評価の表示に必要な修正を加えます。なお、エージェントの完了報告テキストだけを鵜呑みにせず、必ず次の手順で実際の差分とテスト結果を自ら確認することが重要です。

## 差分をレビューする

AI が生成した変更は、どれほど小さく見えても、マージ前に人間の目でレビューする必要があります。Copilot app の機能を使って差分を確認しましょう。

1. 会話入力欄の上部にある **Changes**（Open changes）を選択します。Windows App 1.1.20 では右側のパネルに **Changes** が開き、変更されたファイル数とコード差分が表示されます（パネル自体の開閉は右上の **Toggle panel** で切り替えられます）。

   ![会話欄の Changes と右側の差分パネル](../../_images/app-1.1.20-20260913-changes.png)

2. ゲームカードの描画を担う主要ファイル `src/components/GameCard.astro` にコードが追加されていることを確認します。通常は次のように、評価が存在する場合は数値を表示し、`starRating` が `null` の場合は "No rating yet" を表示する小さなブロックが追加されます。

   ```astro
   {game.starRating !== null ? (
       <span class="text-xs font-medium px-2.5 py-0.5 rounded bg-amber-900/60 text-amber-300" data-testid="game-rating">
           ★ {game.starRating} / 5
       </span>
   ) : (
       <span class="text-xs font-medium text-slate-500" data-testid="game-rating-empty">
           No rating yet
       </span>
   )}
   ```

> [!NOTE]
> すべての生成 AI ツールと同様に、Copilot の出力は決定論的ではなく確率的に変動するため、実際に生成されるコードの記述は上記と完全に一致しない場合があります。ただし、ロジック自体は概ね同等のものになります。

## 変更を確認する

生成されたコードを目視で確認するだけでなく、App の Run メニューから開発サーバーを起動し、ブラウザー上で実際の表示を確認します。

> **確認済みの起動経路（Windows App 1.1.20）：** `.github/github-app.yml` が適用されたセッションの Run メニューを使用します。メニューに実行項目が表示されない場合は、演習用コピーの設定内容と適用状態を講師と一緒に確認してください。

![Copilot App の検証報告と Browser パネルに表示された星評価付きゲームカード](../../_images/app-1.1.20-20260913-star-rating.jpg)

2026年9月13日の実機検証における実装では、既存コンポーネントである `StarRating` をカード側から再利用し、`null` の場合のみカード内で `No rating yet` を表示する構成としました。カードの実レンダリングを検証するテストにおいて `4.2`、`0`、`null` の各境界値とリンク構造を検証し、単体テスト30件、E2Eテスト21件、lint、型検査のすべてが成功することを確認しています。また、ブラウザー上でも既存データの一覧が正しく表示されることを確認しました。さらにアクセシビリティ対応として、評価には `Rating: X out of 5 stars` という読み上げラベル（アクセシブルネーム）も付与しています。

なお、検証用 PR #9 の作成にあたっては、App のエージェントが `gh` コマンドを経由して作成を行い、CI の全4ジョブが正常に通過しました。当時、App 組み込みの PR 作成ツールはアカウント連携エラーで失敗したため、本検証では後述する UI 上の Create PR 経路の成功例としては計上していません。その後、App 内の「My work」→「PR #9」→「Ready to merge」→「Merge pull request」を通じて通常マージの成功を確認し、次章で作成する新規 worktree へ星評価の変更が正常に継承されたことを確かめています。詳細な経緯は [実走記録](../material/verification.md) を参照してください。

### 開発サーバーの起動と停止手順

1. セッション上部の **Run options** から **Run development site** を選択します。ボタンの表示が **Run Run development site** になっている場合は、それをクリックして起動します。すでに **Stop Run development site** と表示されている場合は稼働中ですので、再クリックせずそのまま次の手順へ進んでください。

   ![App 上部の Run メニューと会話・Files パネル全体](../../_images/app-1.1.20-20260913-run-menu.png)

2. サーバーが起動したら、**Browser** パネルに表示されるローカル URL を確認します（実走環境では `http://localhost:4321/` が自動的に表示されました）。
3. トップページの各ゲームカードに、期待通り星評価が表示されていることを確認します（未評価データの表示処理についてもテスト結果と合わせて確認してください）。
4. 確認が完了したら、セッション上部の **Stop Run development site** を選択してサーバーを停止します。なお、サーバー停止後も Browser パネルに直前の画面描画がそのまま残る場合がありますが、画面が残っていること自体をサーバー稼働の証拠とは見なさないよう注意してください。

> [!TIP]
> App 内で組み込みターミナルを開く場合は、**Toggle panel** → **+**（Add tab）→ **Terminal** からアクセスできます（この UI 導線の存在は実機で確認済みです。ただし、ターミナルから直接コマンド入力してサーバーを起動する手順は、本章の公式実走手順には含めていません）。

## 最初の pull request を作成してマージする

変更内容と動作確認に問題がないことが確認できたので、コードをリポジトリへ反映（リリース）します。エージェントに pull request の作成を依頼し、自身でレビューを行ったうえでマージを実施します。本章では手動でマージ管理を行いますが、後続のレッスンでは Copilot を用いてこれらの工程を自律的に処理させる方法も扱います。

> **実機で確認した PR 経路（Windows App 1.1.20）：** GitHub 連携セッションにおいては、次章で作成する PR #10 において **Create PR** ボタンによる作成が成功しました。作成後は **My work** → 対象 PR → **Changes** から差分を表示でき、**Ready to merge** 画面で CI チェック結果、未解決コメントの有無、**Merge pull request** ボタン、およびマージ方法の選択肢を確認できます。ただし、本章の星評価をローカルフォルダー経由で作業した際は App 組み込みの PR 作成が失敗したため、接続形態の違いに応じた挙動の差に留意してください。

1. 画面右上にある **Create PR** を選択します。
2. ブラウザー認証を求められた場合は、**Sign in with your browser** を選択し、画面の指示に従って GitHub アカウントで認証します。
3. Copilot が pull request の作成処理を開始します。
4. PR が作成されると、Copilot はリポジトリ上でトリガーされた CI ワークフローの実行状態を監視します。ジョブが正常に完了すると、右上のボタンが **Ready to merge** へ変化します。これは PR のマージ準備が整ったことを示しています。
5. チャット欄のすぐ上にある **PR** バブルを選択すると、レビューペインで対象の pull request が開きます。必要に応じてここで最終レビューを行います。
6. 確認後、**Ready to merge** を選択します。
7. 表示されたダイアログウィンドウで **Merge pull request** を選択し、pull request を main ブランチへマージします。

これで、最初の機能追加が Web サイトへ正常に反映されました。

<a id="cli-fallback"></a>

> **講師向け：** 参加者の環境でトラブルが生じ、緊急に作業を保全する必要がある場合のみ [対応手順](../material/emergency-cli.md#chapter-2) を参照してください。なお、CLI 側で実装が完了しても、本章における App 操作の完了とは見なしません。

## まとめと次のステップ

最初のエージェントセッションを開始し、最初の変更を無事にリリースできました。本章で実施した主な内容は次の通りです。

- エージェントセッションを開始し、その画面構成と作業ディレクトリの扱いを理解した
- ゲームカードに小規模で対象を絞った変更を加えるようエージェントへ指示した
- ワークスペースの差分ビュー（Changes）でコードの変更内容をレビューした
- アプリをローカル開発サーバーで起動し、ブラウザー上で星評価の表示を確認した
- pull request を作成し、CI 完了を確認したうえで手動マージを行った

次は、エージェントの一貫したコーディング品質を保つため、リポジトリにカスタム指示（Custom Instructions）の標準ルールを追加します。バックログにある Issue を起点として作業を進めましょう。[レッスン 3「カスタム指示による Copilot のガイド」][next-lesson] へ進んでください。
