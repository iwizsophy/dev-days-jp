## 3.1 章の概要

GitHub Copilot appのエージェントに実装を依頼した後は、生成された差分と動作を確認し、変更を取り込むか判断するのが受講者の役割です。この章では、変更の範囲を絞り、依頼に含めた仕様と確認条件を、差分、画面、テストと照合する方法を学びます。

小さな表示の変更にも、データの値をどう解釈するか、既存のどの動作を保つかという判断が含まれます。作業対象と実行場所を確かめてから、依頼、レビュー、動作確認、PRのマージまでを一通り体験しましょう。エージェントの完了報告だけで判断せず、実際の差分と動作を確かめます。

### 3.1.1 この章で学ぶこと

| 項番 | この章で行うこと | 期待される効果 |
| :---: | :--- | :--- |
| 1 | 実装セッションの開始元、作業ディレクトリ、ブランチと実行環境を確認する | 意図した作業対象と実行場所で変更を始められるか判断できる |
| 2 | 変更後の表示、データの扱い、既存の構造やリンクを保つ条件と確認方法を伝える | 変更の範囲と、実装後に満たすべき条件をエージェントと共有できる |
| 3 | 差分、画面、テスト結果を依頼の仕様と照合し、不足があれば修正を依頼する | エージェントの完了報告と検証結果を基に、変更が依頼を満たすか判断できる |
| 4 | PRをレビューし、CIの全ジョブの成功を確認して、手動でmainへマージする | 変更を取り込む可否を判断し、mainに反映されたことを確認できる |

## 3.2 取り組む前に

[前章][prior-lesson]でAppに接続したTailspin Toysの演習用リポジトリを使います。教材用テンプレートに含まれる設定をAppで承認し、そのプロジェクトの入力欄へ進めることを確認してください。実装を始めるセッションでは、Node.jsのバージョンも確認します。

本章の作業場所は、Tailspin Toysの演習用リポジトリのmainを基に作る新しいworktreeです。Appでローカルリポジトリを実行場所に選ぶと、既存の作業フォルダーを使います。編集前にエージェントの作業対象となるプロジェクト、作業ディレクトリ、ブランチを確かめ、同じcheckoutを使う複数セッションでは同時に編集しないようにします。

## 3.3 ケース

第2章では、GitHub Copilot appのIssuesでTailspin Toysの演習用リポジトリの課題を読み、相談用のChatsでエージェントにworktreeの仕組みを質問しました。このケースでは、前章で接続したTailspin Toysの演習用プロジェクトで実装用のエージェントセッションを開始し、ゲームカードの星評価表示を題材に最初のコード変更を行います。

| 項番 | 観点 | このケースで扱う内容 |
| :---: | :--- | :--- |
| 1 | 状況 | 演習用サイトTailspin Toysでは、各ゲームのデータに星評価の値があり、ゲームの詳細ページにも表示されています。一方、トップページの一覧カードには星評価がありません。 |
| 2 | 課題と理由 | Tailspin Toysの利用者は、一覧カードだけではゲームの星評価を比較できません。ゲームを選ぶときの判断材料を増やすために対応します。 |
| 3 | 解決策 | 既存の評価値をトップページの各一覧カードに表示し、再利用できる表示部品があれば使います。0点と未評価を表示し分け、既存のカード構造とゲーム詳細へのリンクを保ちます。 |

実装を依頼する前に、Tailspin Toysのゲームカードで0点と未評価をどのように表示し分けるか考えてみましょう。エージェントが生成したコードを読む際も、次の手順でその予想と結果を比べます。

<a id="セッションを開始する"></a>

### 3.3.1 セッションと環境を確認する

Appに接続したTailspin Toysの演習用プロジェクトで、新しい実装セッションを開始してください。エージェントの作業場所を確認してから変更を依頼します。

1. GitHub Copilot appを開きます（起動済みの場合はそのまま進めます）。
2. サイドバーの**Projects**で自分の演習用プロジェクトを選び、横にある**`+`**から新しいセッションを開きます。演習用プロジェクトを右クリックし、**`+` New session**を選ぶ方法もあります。

3. **New** 画面の入力欄下部に、自分の演習用プロジェクト名が表示されていることを確認します。実行場所は **New worktree**、開始元は **main** を選びます。モードは、応答を読みながら指示を加える **Interactive** で進めます。

   ![New sessionで確認する対象プロジェクトとNew worktree、main](../../_images/app-20261004-public/app-20261004-02-new-session.jpg)

   Interactive・Plan・Autopilotの違いは[公式のモード説明][agent-sessions]で確認できます。

<a id="実装前の環境確認"></a>

#### 3.3.1.1 実装前の環境確認

ローカルPCのターミナルとAppの実装セッションでは、実行するNode.jsが異なる場合があります。これからエージェントがテストやビルドを行うセッションでのNode.jsのバージョン確認は、環境を原因とするエラーかを判断するための手がかりです。

1. 機能の実装を依頼する前に、次のプロンプトを送信します。

   ```plaintext
   このセッションで node --version を実行し、コマンドの出力をそのまま報告してください。
   作業ディレクトリと現在のブランチも確認してください。
   ファイル変更、追加インストール、PR作成はしないでください。
   ```

2. ツールの実行結果で、**Node.js 24系の24.19.0以降**が使われていることを確認します。作業ディレクトリとブランチも、今回のworktreeのものか確かめます。コマンドが見つからない場合や要件を満たさない場合は、[前章までのNode.jsの準備](1-prerequisites.md#確認とインストール手順)を見直します。Node.jsを切り替えた後はAppを再起動し、このセッションで再確認してから実装へ進みます。

エージェントの説明に書かれたNode.jsのバージョンを、ツールのコマンド出力と照合します。環境の確認ができたら、同じ実装セッションで星評価の表示を依頼します。

<a id="星評価の実装を依頼する"></a>

### 3.3.2 星評価の実装を依頼する

1. 環境を確認した実装セッションの入力欄に次のプロンプトを入力し、星評価の表示をエージェントに依頼します。

   ```plaintext
   ゲームカードに各ゲームの星評価を表示してください。
   Game 型には starRating があり、5点満点の数値、または未評価を示す null が入ります。
   src/components/GameCard.astro の各カードに表示し、null の場合は「No rating yet」と表示してください。
   0は評価値として表示し、未評価と区別してください。
   詳細ページの既存の評価表示と関連コンポーネントを確認し、再利用できるものを使ってください。
   変更は小さく保ち、カードの構造やゲーム詳細へのリンクは組み替えないでください。
   通常データを変更せず、GameCardの実際のレンダリング結果で4.2、0、5、nullの表示とリンク構造をテストしてください。
   利用するNode.jsのバージョン、変更内容、実行したテストと結果を報告してください。
   PR作成とマージは、後で指示するまで行わないでください。
   ```

2. <kbd>Enter</kbd> キーを押して、プロンプトを送信します。

エージェントが行うのは、Tailspin Toysのコードの調査と、ゲームカードへの星評価表示に必要な変更です。完了報告を受けたら、次の手順で実際の差分とテスト結果を読み、依頼した仕様と照合してください。

<a id="差分とテストをレビューする"></a>

### 3.3.3 差分とテストをレビューする

エージェントが生成した星評価の変更は、マージ前に受講者がレビューします。実装セッションのChangesで対象ファイルと差分を読み、星評価を加えるために何が変わったか確かめましょう。

1. 会話入力欄の上部にある **Changes**（Open changes）を選択します。変更されたファイルの一覧とコード差分を確認します。

   ![ChangesでGameCardの星評価の表示と既存構造を確認する](../../_images/app-20261004-public/app-20261004-02-changes-game-card.jpg)

2. ゲームカードの描画を担う `src/components/GameCard.astro` に、星評価を表示する変更があることを確認します。

<a id="値の意味からレビューする"></a>

#### 3.3.3.1 値の意味からレビューする

ゲームの星評価を`if (game.starRating)` のように値の真偽だけで分けると、JavaScriptでは `0` も偽として扱われます。そのため、0点が未評価と表示される実装になっていないか確認します。Tailspin Toysの星評価データでは`null`が未評価です。数値と未評価の区別を明示してください。

| 項番 | 入力 | 期待する意味と確認内容 |
| :---: | :--- | :--- |
| 1 | `4.2` | 小数を含む評価を5点満点として表示する |
| 2 | `0` | 0点という評価を表示し、No rating yetにしない |
| 3 | `5` | 上限の評価を表示する |
| 4 | `null` | No rating yetを表示し、数値の評価を表示しない |

ゲームカードへの変更後も、既存のタイトルや説明、ゲーム詳細へのリンクが保たれているか確認します。星の形や色だけに意味を任せず、テキストや読み上げ用の名前からも評価値が分かることを確かめましょう。数値表示と `No rating yet` が同時に出ないこともレビューの対象です。

星評価の表示を検査するテストのコードも、実装セッションのChangesで読みます。テスト内に条件式だけをコピーして検査しても、実際のGameCardにその実装が使われたことは確認できません。星評価の境界値を渡してコンポーネントをレンダリングし、その出力に期待した表示とリンクがあるかを検査する必要があります。テストが不足していれば、同じ実装セッションで次のように追加指示をエージェントへ送ります。

```plaintext
テストがGameCard.astroの実際のレンダリング結果を検査しているか確認してください。
4.2、0、5、nullについて、表示される内容と表示されない内容を確認し、ゲーム詳細へのリンクも検査してください。
通常のCSVやDBは変更せず、テスト用データを使ってください。
不足を修正し、lint、型検査、単体テスト、E2E、buildの結果を報告してください。
PRはまだ作成しないでください。
```

<a id="ブラウザーで動作を確認する"></a>

### 3.3.4 ブラウザーで動作を確認する

Appで星評価を実装したセッションのRunメニューから、Tailspin Toysの開発サーバーを起動してください。ブラウザーでゲームカードの表示を確認し、利用者に見える結果を、依頼した仕様と比べます。

> [!NOTE]
> `.github/github-app.yml` が適用されたセッションのRunメニューを使用します。メニューに実行項目が表示されない場合は、演習用コピーの設定内容と適用状態を講師と一緒に確認してください。

![ブラウザーで表示したゲームカードの星評価と詳細へのリンク](../../_images/app-20261004-public/app-20261004-02-star-rating.jpg)

Tailspin Toysの通常データに含まれる21件のゲームはすべて数値評価を持つため、そのデータを使う画面だけでは`null`の表示を確認できません。ゲームカードの画面と、テスト用データによる境界値の検査を合わせて判断します。

<a id="開発サーバーの起動と停止手順"></a>

#### 3.3.4.1 開発サーバーの起動と停止手順

1. 星評価を実装したセッション上部の **Run options** から **Run development site** を選択します。

    - ボタンが **Run Run development site** と表示されている場合は、クリックして起動します。
    - すでに **Stop Run development site** と表示されている場合は稼働中ですので、そのまま次の手順へ進んでください。

   ![Run optionsからRun development siteを起動する](../../_images/app-20261004-public/app-20261004-02-run-menu.jpg)

2. **Run**のターミナルに表示されたローカルURLを開きます。**Browser**パネルが自動で開かない場合は、表示されたURLを別ブラウザーで開いてください。ポート番号は自分の実行結果を使います。
3. Tailspin Toysのトップページの21件のカードに星評価が表示され、タイトル、説明、詳細へのリンクが保たれていることを確認します。通常画面で出現しない `null` と境界値は、前節のレンダリングテストの結果で確認します。
4. 任意のカードから詳細ページへ移動し、評価値が一覧と一致することを確認します。一覧へ戻れることも確かめてください。
5. 確認後、セッション上部の **Stop Run development site** を選択します。Runのターミナルで **Shell session ended** などの終了表示を確認してください。停止後もブラウザーには直前の画面が残る場合があるため、その画面だけで稼働中と判断しないようにします。

<a id="最初の-pull-request-を作成してマージする"></a>

### 3.3.5 最初のPull Requestを作成してマージする

星評価の動作確認を終えた変更を、PRで自分の演習用リポジトリのmainへ取り込みます。この章で使うのは手動マージです。後の章では、同じ確認を経てエージェントにマージを任せる方法も体験します。

星評価のPRは実装に使ったセッションから作成し、差分やCIの結果をApp内で確認できます。作成済みのPRをAppのサイドバーから開く入口は**Pull requests**です。機能の説明は[GitHub公式のPR管理手順][managing-issues-prs]も参照してください。

このテンプレートの[開発ルール][template-issue-rule]では、変更に対応するIssueを作ることを求めています。本章では要件を直接伝えて実装しましたが、PRを作るときに、その目的と受け入れ条件をIssueにも記録します。IssueとPRを関連付けると、変更の理由と実装結果を一緒に追えます。関連付けの方法は[GitHub公式の説明][linking-issue-pr]を参照してください。

1. 星評価を実装したセッションの画面右上にある **Create PR** を選択します。
2. ブラウザー認証を求められた場合は、**Sign in with your browser** を選択し、画面の指示に従って認証します。
3. CopilotによるPRの作成処理と、関連するIssueの作成・選択を確認します。Issueを求められた場合は、次のプロンプトを送信します。既に星評価のIssueが作成されていれば、そのIssueを使います。

   ```plaintext
   自分の演習用リポジトリで、今回のゲームカードへの星評価表示に対応するIssueを確認してください。
   同じ変更を扱うIssueがあれば再利用し、なければCONTRIBUTING.mdに従って作成してください。目的と受け入れ条件には、このセッションで合意した星評価の仕様を記録してください。
   そのIssueを今回のPRに関連付けてください。PRの取り込み先は自分の演習用リポジトリのmainとし、マージはまだ行わないでください。
   ```
4. 作成されたPRのリポジトリが自分の演習コピーで、取り込み先が **main** であることを確認します。本章では **Agent merge**を**Off** にして、手動でマージするところまで進めます。
5. 同じ実装セッションのチャット欄のすぐ上にある**PR**バブルを選択し、レビューペインで作成されたPRの内容を最終確認します。関連Issueのタイトルと本文が今回の星評価の変更を表し、同じ演習用リポジトリのIssueであることも確認してください。
6. **Ready to merge** を選択し、ダイアログのCI結果を確認します。このボタンの表示だけでは、CI全成功とは判断できません。**Checks are running** や実行中のジョブがあれば待ち、すべてのジョブの成功を確認します。表示が更新されない場合は画面を開き直し、必要に応じてGitHub Webの同じPRでも照合してください。

   ![CI全ジョブの成功とAgent merge Offを確認して手動でマージする](../../_images/app-20261004-public/app-20261004-02-pr-ci-passed.jpg)

7. 差分、テスト結果、未解決のレビュー指摘を確認したうえで、**Merge pull request** を選択してmainへマージします。
8. AppとGitHub Webで対象PRが **Merged** になったことを確認します。次章では、マージ済みのmainから新しいworktreeを開始します。

これで星評価の変更が自分の演習用リポジトリのmainへ取り込まれました。公開サイトへのデプロイは本章では扱いません。

<a id="振り返り"></a>

## 3.4 結果の整理と振り返り

Tailspin Toysのゲームカードへの星評価表示をエージェントに依頼し、レビューした変更を自分の演習用リポジトリのmainへ取り込みました。確認したことを整理しましょう。

| 項番 | 確認した根拠 | 判断したこと |
| :---: | :--- | :--- |
| 1 | 作業ディレクトリとブランチ | 今回のworktreeで編集していること |
| 2 | Changes | 既存表示とリンクを保ち、星評価だけを加えていること |
| 3 | 通常データの画面 | 利用者が一覧で評価を読め、詳細ページへ移動できること |
| 4 | レンダリングテスト | 4.2、0、5、nullを仕様に沿って表示し分けること |
| 5 | PRのCIとMerged | 用意された検査に成功し、変更をmainへ取り込んだこと |

「0とnullを分ける理由」「通常の21カードだけでは確認できないこと」「Ready to mergeの表示後に読む情報」を、自分の言葉で説明してみましょう。

最初に予想したゲームカードの表示と、エージェントが生成した実装は一致しましたか。追加指示をエージェントに送った場合は、何が不足し、修正後にどの根拠を得られたかを振り返ります。次の課題でも、依頼、差分、画面、テストのつながりを追います。

## 3.5 補足

<a id="小さな変更から始める理由"></a>

### 3.5.1 小さな変更から始める理由

エージェントとの開発に慣れる段階で小さな変更から始めるのは、エージェントへの依頼、差分のレビュー、動作確認、PRのマージまでを一通り経験し、各段階で自分が何を判断するかをつかむためです。最初から複数の機能をまとめて任せると、要件の伝え方、実装、環境のどこに問題があったのかを追いにくくなります。目的と確認対象を絞れば、予想と結果の違いを見つけて修正し、同じ確認を繰り返しやすくなります。

Tailspin Toysの星評価表示では、各ゲームの評価値がすでにデータにあり、ゲーム詳細ページにも表示されています。本章で追加するのは、ホームページの一覧カードにもその値を表示する機能です。データの収集や保存方法は変えず、既存の表示部品を再利用できるか調べます。カードの構造と詳細ページへのリンクを保つ条件も定めているため、評価の表示とその確認に集中できます。ただし、0点という評価値と、未評価を表す`null`の表示を分ける判断やテストは、この小さな変更にも必要です。

ここでいう変更の小ささは、修正行数やファイル数だけで決まりません。変更の目的が一つで、その目的に必要な実装と検証をまとめてレビューできることが判断の基準です。星評価の表示コードと、その表示を確かめるテストは同じ目的に含まれます。無関係なレイアウトの変更やデータ保存方式の変更まで一緒に進めると、目的も確認範囲も広がります。GitHub公式も、[一つの目的に絞った小さなPR][focused-pull-requests]を勧めています。

実務のIssue駆動開発では、Issueに「なぜ変えるのか」「何を変えるのか」「何を満たせば完了か」を記し、その合意を基に実装とレビューを進めます。Issueを作っただけで、適切な作業単位になるわけではありません。担当者とレビューする人が、目的と完了条件を同じように理解し、結果を確かめられる範囲に整理します。大きな課題を分割するときも、元の目的との関係と、他の課題への依存を残します。[GitHub公式のIssueの分割に関する説明][issue-scoping]では、課題の分割と依存関係の明確化を案内しています。

| 項番 | 判断すること | 実務で確認すること |
| :---: | :--- | :--- |
| 1 | 目的 | 利用者のどの問題を解決するかを説明できるか。別の目的の改修が混ざっていないか |
| 2 | 完了条件 | 期待する動作、例外となる入力、保つべき既存動作を示し、結果を確かめられるか |
| 3 | 変更と検証の範囲 | 目的に必要な実装とテストをそろえ、レビューする人が差分と結果を追えるか |
| 4 | 依存関係 | 他の変更が先に必要か。分割する場合に、実装・レビュー・取り込みの順を説明できるか |

たとえば実務で「ゲームを比較しやすくする」という大きな課題に取り組む場合、一覧カードへの星評価表示を一つのIssueとして切り出せます。目的は利用者が評価を比較できること、完了条件は評価値・0点・未評価の表示と既存リンクの維持です。検索やレイアウトの改修は、それぞれの目的と完了条件を決めて別の課題として検討します。一方、評価表示にAPIやデータ保存の変更が不可欠なら、その依存も含めて実装・検証の範囲を決めます。分割する場合は、取り込みの順と途中の状態で利用者に影響が出ないかも確かめましょう。

IssueとPRを必ず一対一にする必要はありません。一つのIssueを複数のPRで進める場合は、それぞれが担う目的と取り込み順を示します。同じPRの中で意味のある単位にコミットを分けることも、レビューを助けます。ただし、コミットを細かくするだけでは、Issueの目的や完了条件が明確になるわけではありません。

Copilotへ渡す課題についても、解決する問題、受け入れ条件、変更箇所を明確にする考え方は、[Copilot cloud agent向けの公式ガイド][copilot-task-scoping]を参考にできます。本章では受講者が要件を直接伝え、最初の開発の流れを学びます。第4章からはIssueを起点に進めますが、目的と完了条件を共有し、必要な差分と検証結果を基に取り込みを判断する考え方は共通です。

<a id="352-セッションとworktreeの役割"></a>

### 3.5.2 作業場所を分け、変更を次の作業へ引き継ぐ

複数の変更を扱うときは、どのプロジェクト・作業フォルダー・ブランチで編集しているかを確かめます。作業場所を分けたことと、レビューした変更が取り込み先に反映されたことは別です。次の作業でその変更を使うなら、開始元に含まれているかも確認してください。

GitHub Copilot appの**セッション**とは、特定のプロジェクトを対象としてエージェントと対話を行う作業空間です。Appのサイドバーのプロジェクト一覧から起動できます。

Appでセッションを開始するときは、[GitHub公式のセッション手順][agent-sessions]に沿って、新しいworktree、ローカルリポジトリ、クラウドの実行環境を選べます。worktreeを分けることは作業中のファイルを分けるためであり、変更が自動的に取り込み先へ反映されるという意味ではありません。

本章で選ぶ実行場所は**New worktree**です。演習用リポジトリのmainを基にした別の作業場所で変更します。受講者がレビューし、PRを自分のmainへマージして、変更を次章で利用できる状態にします。

セッションでの説明と実際の作業を照合するため、会話、操作履歴、差分を合わせて読みます。

| 項番 | 要素 | 確認する内容 |
| :---: | :--- | :--- |
| 1 | Chat | エージェントへの指示と回答 |
| 2 | Tool Activity | 調査や編集、検査で実行された操作 |
| 3 | Changes | 変更ファイルとコードの差分 |

> [!TIP]
> App内で組み込みターミナルを開く場合は、**Toggle panel** → **`+`**（Add tab）→ **Terminal** からアクセスできます。開発サーバーの起動・停止には、実装セッションのRunメニューを使います。

<a id="依頼に含める仕様と確認方法"></a>

### 3.5.3 依頼に含める仕様と確認方法

実務でエージェントに実装を依頼するときは、利用者のどの問題を解決し、変更後に何ができる状態にするかを共有します。そのうえで、実装が満たすべき動作と、その動作を確かめる方法を記します。期待する結果を明示しておけば、依頼した人とエージェントが同じ基準で実装や修正を判断できます。

受け入れ条件は、実装後の結果を見て、依頼を満たしたか判断できる条件です。通常の入力だけでなく、値がない場合や上限・下限など、仕様によって動作が変わる条件も示しましょう。既存の動作やデータを保つ必要がある場合は、その対象も記します。入力例と期待する結果を対にすると、エージェントに仕様を伝えやすく、レビューする人も確認する対象を選べます。

本章では、ケースの説明で、利用者がゲーム一覧で評価を比較できるようにする目的を共有しています。依頼文には、その目的に沿って、ホームページのカードに何を表示し、どの既存動作を保ち、どう確かめるかを具体化しました。実務で共有する内容と、本章での適用は次のとおりです。

| 項番 | 実務で依頼に含めること | 星評価のケースでの適用 |
| :---: | :--- | :--- |
| 1 | 目的と期待する動作。対象の利用者・画面・変更後の結果を示す | ゲーム一覧で評価を比較できるよう、ホームページの各ゲームカードに星評価を表示する |
| 2 | 入力と期待する結果。通常の値、境界値、未入力などの扱いを示す | 5点満点の数値と、未評価を表す`null`を区別する。`0`は評価値として表示し、`null`ではNo rating yetを表示する |
| 3 | 変更と操作の範囲。変更する対象、維持する動作・データ、PR作成などの操作範囲を示す | GameCardに表示を追加し、カード構造・詳細ページへのリンク・通常データを保つ。PR作成とマージは後の指示まで待つ |
| 4 | 調査に必要な情報。関連する画面・コード・仕様を示し、既存実装を確認させる | 詳細ページの評価表示と関連コンポーネントを調べ、再利用できる表示部品を使う |
| 5 | 確認方法と報告。受け入れ条件を確かめる検査と、結果・未確認の項目の報告を指定する | GameCardの描画結果を`4.2`、`0`、`5`、`null`でテストし、表示とリンク構造を確かめる。実行したテストと結果を報告する |

実務では、依頼する時点で実装先のファイルやデータの意味が分からない場合もあります。分かっている事実と未確認の点を分け、まず関連コードや仕様の調査を依頼しましょう。調査で不明点や選択肢が見つかったら、人が判断する点を確認し、合意した条件を依頼文やIssueへ反映してから実装へ進みます。ファイルパスは、対象が分かる場合に調査の手がかりとして示すもので、依頼の必須条件ではありません。

本章では実装先が分かっているため、`src/components/GameCard.astro`を指定しました。一方、表示部品を再利用できるかは既存実装を調べるよう依頼しています。これは、一覧と詳細ページに同じ評価の表示を別々に作り、表示が食い違うことを避けるためです。通常画面で星が見えるだけでは、`null`の扱いやリンクの維持まで確認できないため、実際のGameCardの描画結果を検査する条件も含めました。PR作成とマージを後の指示まで待つ条件は、受講者が実装を確認し、次の操作へ進む時点を判断するためです。実務でも、変更の性質に合わせてテストや画面確認を選び、実装の差分と検査結果を受け入れ条件に照らして判断します。

目標から具体的な要件へ進み、入力と出力の例で曖昧さを減らす考え方は、[GitHub公式のCopilot Chatのプロンプト設計][prompt-engineering]で説明されています。問題と受け入れ条件、関連するファイルを明確にする考え方は、[Copilot cloud agent向けの課題整理のガイド][copilot-task-scoping]も参考にできます。いずれも依頼内容の整理に関する参考資料です。

<a id="0とnullを区別するコードの読み方"></a>

<a id="354-0とnullを区別するコードの読み方"></a>

### 3.5.4 生成されたコードを仕様から読む

Copilotが生成したコードを読む目的は、依頼した仕様が実装されているかを判断することです。同じ動作を実現するコードにも、条件の書き方や部品の使い方が異なる実装があります。教材の説明例と形が違う場合も、入力に対する結果と、既存の構造・動作を保つ条件を基に確認します。

星評価のケースでは、`Game.starRating`に5点満点の数値か、未評価を示す`null`が入ります。[JavaScriptでは、`0`と`null`はいずれも真偽値として判定すると偽になります][js-falsy]。そのため、`if (game.starRating)`のように値の真偽だけで分けると、0点も未評価として扱うことになります。コードを読むときは、値の意味と、実装が判定している条件を照合します。

次の説明例は、`game.starRating !== null`で、未評価かどうかを判定しています。このケースのデータの条件では、`4.2`、`0`、`5`は数値を表示する側へ進み、`null`はNo rating yetを表示する側へ進みます。数値の大きさで分けているのではなく、未評価を表す値かどうかで分けるため、0点と未評価を区別できます。

   ```astro
   {game.starRating !== null ? (
       <span class="text-xs font-medium px-2.5 py-0.5 rounded bg-amber-900/60 text-amber-300" data-testid="game-rating">
           ★ {game.starRating} / 5
       </span>
   ) : (
       <span class="text-xs font-medium text-slate-500" data-testid="game-rating-empty">
           No rating yet
       </span>
   )}
   ```

このコードは、評価を表示し分ける条件の説明例です。実装で既存の`StarRating`を再利用すれば、数値側がコンポーネントの呼び出しになることもあります。条件の判定を部品の中で行う実装も考えられます。同じ条件式がGameCardに直接書かれていなくても、呼び出し先を含めて、各入力に対する表示が仕様を満たすかを読みます。

説明例には、カード全体の構造やゲーム詳細へのリンクは示していません。星評価の表示が正しくても、既存部品の再利用、カードとリンクの維持、通常データを変更しない条件まで満たしたとは判断できません。実務でも、生成された実装の差分と関連する部品を読み、実際のテスト結果を受け入れ条件に照らして、採用や修正を判断します。本章では[差分とテストをレビューする手順](#差分とテストをレビューする)で確かめます。

生成コードを人がレビューし、意図やプロジェクトの条件に合うかを検査する考え方は、[GitHub公式のAI生成コードのレビューガイド][review-generated-code]も参考にできます。

<a id="差分画面テストciで確かめること"></a>

### 3.5.5 差分、画面、テスト、CIで確かめること

実装の確認では、変更の性質と受け入れ条件に合わせて、必要な確認方法を選びます。差分では変更の範囲と実装の内容、ブラウザーでは利用者に見える表示や操作、テストでは入力に対する期待どおりの動作を確かめます。CIでは、共有された環境で用意された自動検査が成功したかを確認します。

一つの確認方法に成功しても、そこで扱っていない条件まで満たしたとは判断できません。各結果を受け入れ条件に照らし、確認できたことと未確認の点を整理して、修正や取り込みを判断してください。

この章の星評価の実装では、コードの差分で変更の範囲、ローカルのTailspin Toysの画面で利用者に見える結果、テストで通常画面に現れない条件を確認しました。それぞれ確認できる対象が違うため、どれか1つの成功で他を省略せず、結果を合わせて判断します。

星評価のPRでは、AppのReady to mergeボタンがマージ可能に見えることと、用意された検査がすべて成功したことは別なので、ジョブの結果まで読みます。
