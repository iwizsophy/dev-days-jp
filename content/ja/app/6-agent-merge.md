> **この章の確認範囲：** 2026年9月13日に Windows の App 1.1.20 実機にて、Agent merge による PR 作成と CI 全4ジョブ成功後の自動マージを確認済みです（掲載画像は検索機能 PR の画面例ですが、操作導線は同一です）。なお、CI 失敗や競合の自動修正機能は実機未検証です。詳細は [UI 確認表](../material/ui-check.md) を参照してください。

前章までで、フィルター機能のコード実装、単体・E2E テストの実行、そして Playwright MCP を用いたブラウザー手動操作による検証がすべて完了しました。開発サイクルの最終ステップは、コードを main ブランチへマージしてリリースすることです。

ここまでのレッスンでは、星評価機能やドキュメント規約の pull request において人間が **Merge pull request** をクリックして手動マージを行いました。本レッスンでは、PR 作成から CI 監視、問題修正、そして最終マージに至る一連のライフサイクル管理をアプリ内の自律機能である **Agent Merge** に委ねます。

このレッスンでは、次の内容を学習します。

- Agent Merge の役割と、マージのライフサイクルを自律管理する仕組みを理解する
- フィルター機能の実装セッションで Agent Merge を有効化する
- PR の自動作成、CI 実行の監視、全チェック通過後の自動マージの完了を確認する

## シナリオ

本ワークショップを通じて、コード生成、自動テスト、MCP による実ブラウザー操作と、段階的に自動化のレベルを引き上げてきました。Tailspin Toys では開発速度をさらに向上させるため、検証済みの pull request に対する機械的なマージ待機と最終処理を自動化する手法を検討しています。

## Agent Merge の概要

**Agent Merge** は、pull request の作成からマージ完了までの最終工程をエージェントに自律実行させる機能です。

Agent Merge を有効にすると、エージェントは PR の状態を常時監視し、以下のようなマージを妨げる障害が発生した場合に自律的に対処を試みます。
- CI チェック失敗時の原因調査と修正コードのプッシュ
- レビューコメントへの対応
- main ブランチとの競合（コンフリクト）発生時のリベースや解消作業

そして GitHub 上でマージ条件が満たされ次第、エージェント自身が pull request を自動マージします。この処理はバックグラウンドで動作し、アプリを再起動してもタスクは継続され、マージが完了すると自動的に終了します。

これまでの手動マージでは、人間が CI の完了を待ってボタンを押す必要がありました。Agent Merge を活用することで、人間は「コードのレビューと承認」という本質的な判断に専念し、承認後の機械的な待機や後処理をエージェントに委託して即座に次のタスクへ着手できるようになります。

## Agent Merge で PR を管理する

コードレビュー、自動テスト、UI 検証を終えたフィルター機能のコードをマージしましょう。Agent Merge を起動し、CI 監視からマージまでをエージェントに任せます。

1. 前章まで作業していたフィルター機能の実装セッションを開きます。
2. 画面右上にある **Create PR** ボタンの右側にあるドロップダウン矢印を選択します。
3. メニューから **Agent merge** を選択します。

   ![App 全体と Agent merge、Create PR、Create draft PR の選択メニュー](../../_images/app-1.1.20-20260913-agent-merge-menu.png)

4. ボタンの表示が **Agent merge** に切り替わります。
5. **Agent merge** ボタンをクリックし、マージの自律プロセスを開始します。

エージェントが pull request の作成と管理を開始します。まずリポジトリの状況を分析して最適な PR を起票します。PR 作成後、エージェントは CI ワークフローの実行状態やレビューステータスを監視します。

6. **Agent merge** ボタン横のドロップダウンを再度開き、**Merge pull request** のチェックボックスを確認します。  
   もし未選択になっている場合は、クリックしてチェックを入れてマージ権限を許可してください（すでにチェックが付いている場合はそのままにします。再度クリックすると許可が解除されてしまうため注意してください）。

   ![PR 作成後の App 全体。Agent merge の Merge pull request はチェック済み](../../_images/app-1.1.20-20260913-agent-merge-permissions.png)

7. リポジトリ上の全 CI プロセス（テスト、lint、ビルド等）が正常に完了すると、Copilot が pull request を自動的にマージします。

### 実機検証における確認記録と注意点

2026年9月13日の実走検証では、次の挙動を確認しました。
- **PR の自動起票**：手順 5 の実行によって **PR #12** が自動起票されました。
- **マージ権限の設定**：手順 6 のドロップダウンメニューを確認したところ、初期状態では「Address reviews」「Fix CI failures」「Resolve conflicts」の 3 項目は有効化されていましたが、**「Merge pull request」は無効（チェックなし）**になっていました。
- **自動マージの成功**：手動で「Merge pull request」にチェックを入れたところ、CI の全 4 ジョブが正常通過した直後に自動マージが実行され、App セッション画面および GitHub の Web 画面の双方でステータスが **Merged** に更新されました。
- **未検証範囲**：本実走では CI が一発で成功し競合も発生しなかったため、**CI 失敗時の自動修正やコンフリクト解消の自律挙動については実機未検証**です。

次章へ進む前に、新しく作成する worktree にこのフィルター機能のマージ結果が正しく継承されていることを確認してください。

## まとめと次のステップ

コードの実装、品質検証、ブラウザー操作、そしてリリースに至る開発ライフサイクルの大部分を自動化しました。本章で実施した主な内容は次の通りです。

- Agent Merge の概念と、PR の自律監視・マージ自動化の仕組みを理解した
- フィルター機能のセッションで Agent Merge を有効化し、マージ権限（Merge pull request）の設定を確認した
- PR 作成から CI 完了の監視、そして自律マージの成功を確認した

次は、エージェントと対話しながら複雑な作業を視覚的に計画・整理する高度な機能である**キャンバス（Canvases）**を活用します。[レッスン 7「キャンバスを使った計画」][next-lesson] へ進んでください。
