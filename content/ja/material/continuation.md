# 講師専用：緊急対応時の作業保全・PR・復帰

本教材の本編は **App シナリオ（演習0〜8）** です。このドキュメントは、App の停止等に伴い講師が作業を保全・復旧するための緊急対応用です。本編の通常ルートではありません（CLI 独立コースを最初からやり直す必要はありません）。

> [!CAUTION]
> **教材リポジトリと演習用コピーの厳格な区別**：
> 教材サイトのリポジトリ（`dev-days-jp`）と、アプリのコードを改修する各自の Tailspin Toys コピーを混同しないでください。以下の Git、npm、Copilot コマンドは、必ず各自の演習用コピー環境で実行します。

## 1. 切り替える前の確認事項（作業ツリーの特定）

1. **エージェントの停止と保存**：App 側で実行中のエージェントセッションを停止し、エディターの編集内容を確実に保存します。
2. **作業場所の特定**：App セッションが使用している作業ディレクトリを確認します。App の worktree はローカルの通常 clone とは異なるパス（`~/.copilot/repos/copilot-worktrees/...` 等）に存在します（クラウドセッションの場合は、作業内容を自身のリモートブランチへ push してローカルへ fetch/checkout してから続行します）。作業場所やブランチが不明な場合は講師と確認してください。
3. **作業ディレクトリの照合**：ターミナルで対象の作業ディレクトリを開き、次のコマンドを実行して、対象リポジトリ、ブランチ、差分を照合します。

```sh
git rev-parse --show-toplevel
git remote -v
git branch --show-current
git status --short
git diff --stat
```

- **リモートの確認**：Git の remote が自身の演習用コピー（フォーク）でない場合は、直ちに操作を中断してください。**参照元である `github/dev-days`、`github-samples/copilot-workshops`、`github-samples/tailspin-toys` に push、Pull Request、Issue を送信してはなりません。**
- **ブランチの選定**：既存の作業ブランチがある場合は新規作成せずそのまま続行します。未着手かつ既定ブランチがクリーンな場合に限り、章に応じた未使用名（例：`git switch -c feature/app-02-rating`）でブランチを新規作成します。

## 2. CLI への課題引き継ぎ

ターミナルで `copilot` を起動します。通常の対話形式で進め、ファイル変更やコマンド実行の許可を求められた際は、必ず内容を確認してから承認してください（App での会話履歴が CLI へ自動的に引き継がれるとは限りません）。

次のプロンプトの角括弧 `[...]` を実際の情報に置き換えて入力し、続いて各章の要件を伝えます。

```text
App シナリオの演習[番号]を、この作業ディレクトリで続けます。
対象は自分の演習リポジトリ[owner/repo]とブランチ[名前]だけです。
要件：[自分の Issue URL と本文、または章の要件]
実装済み：[内容]。止まった点：[内容]。
README、CONTRIBUTING、指示ファイル、既存の差分を読んでください。
まだ変更せず、残りの計画と検証方法を日本語で示してください。
参照元リポジトリへの書き込みは禁止です。
commit・push・PR・merge は個別に依頼するまで実行しないでください。
```

※Issue の番号は演習コピーごとに異なります。自身のリポジトリで Issue のタイトルと本文を確認し、取得できなければ本文を直接貼り付けてください（必要な Issue が存在しない場合は、自身のコピー内だけに新規起票します）。

## 3. 品質確認と Pull Request の作成・マージ

各章の要件確認に加え、`.github/skills/quality-checks/SKILL.md` および README に従って、単体テスト、E2E テスト、lint、型チェックを実行します。失敗した箇所は修正して再検査し、差分を注意深くレビューします（シェルの実行は CLI を一旦抜けるか、別ターミナルで行います）。

1. **ステージングの確認**：`git diff` および `git status --short` を確認し、対象となるソースコード、テスト、ドキュメントのみをステージングします（MCP の一時生成物や認証情報などを含めてはなりません）。
2. **コミットの作成**：`git diff --cached` で意図した変更のみが含まれていることを確認し、commit します。
3. **リモートへの push**：push 先が自身の演習コピーであり、現在のブランチが main ではないことを再確認した上で、`git push -u origin HEAD` で同名ブランチへ送信します。
4. **Pull Request の作成**：GitHub Web 上で、**自身のコピーを base repository とする** PR を作成します（base は自身の既定ブランチ、head は作業ブランチ）。PR 本文には、要件、差分、テスト結果、未確認事項を漏れなく記録します。
   - ※PR 作成先やマージ先に誤って参照元リポジトリが表示された場合は、直ちに操作を中断し、base repository の設定を見直してください。
5. **CI 確認とマージ**：PR の差分および必要な CI がすべて成功したことを確認します。演習2および演習3はレビュー後に自身のコピーへ通常マージして次へ進みます（演習4および演習5はブランチを維持し、演習6でマージします）。

## 4. 次の章への引き継ぎと App への復帰

### 既定ブランチの同期
演習2および演習3のマージ完了後は、元の clone など既定ブランチを保持する作業ディレクトリにおいて、`git fetch origin`、既定ブランチへの切り替え、および `git pull --ff-only` を実行して最新化します（別 worktree で同ブランチがチェックアウトされている場合は、その worktree 内で更新します。未保存の作業ツリーを `git reset --hard` や `git clean` で消去してはなりません）。

### App への復帰原則
本教材では、可能な限り **App 操作への復帰を最優先** とします。
- App へ戻る場合は、CLI のエージェントを終了し、同じ作業ディレクトリおよび作業ブランチを App で開き、実装した変更とテスト結果をセッションに伝えます。
- App で開けない場合は、App 操作を「未完了」とし、講師デモまたは後日実施へ切り替えます（演習4〜6の途中で、新しいセッションを既定ブランチから無闇に始め直してはなりません）。
- **機能体験の記録**：App 固有の機能（Agent Merge、Canvas、Automation）は、通常の PR、Markdown、単発プロンプト等で代用しても「機能体験は未実施」として記録します。実装の到達点と、App 機能の体験状況は明確に分離して管理してください。
