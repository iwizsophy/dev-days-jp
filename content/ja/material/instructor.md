# 講師ガイド：App シナリオを一本の流れで実施する

## 1. 使用する教材とリポジトリの分離

### 教材の配布と受講者環境
- **受講者への配布**：参加者には [App の目次](../app/README.md) のみを配布します。CLI 独立コースや Mona Mayhem は補講用の参考資料です。本編の途中で受講者を移動させてはなりません。
- **演習用リポジトリ**：演習は、[修正済みの非公開テンプレート](https://github.com/iwizsophy/dev-days-tailspin-template) から各自が作成した Tailspin Toys のコピー環境で行います。参加者には事前にテンプレートの閲覧権限を付与してください（取得先を上流リポジトリに戻してはなりません）。
- **教材リポジトリの保護**：受講者が本教材リポジトリ（`dev-days-jp`）内で直接アプリ実装の演習を行わないよう徹底してください。

### 参照元リポジトリの取り扱い
参照元は `github/dev-days`（開催・運営資料）および `github-samples/copilot-workshops`（App シナリオ）です。参照コミットと対象ファイルは `content/ja/sources.json` に記録されています。参照元への push や Pull Request など、いかなる変更送信も一切行いません。

## 2. 講師向け資料と公式イベント運営上の注意点

### 利用可能な公式リソース
- 日本語の [App 講師向け動画](https://www.youtube.com/watch?v=-ZBf4wpLZKg) および [App スライド](https://github.com/github/dev-days/releases/download/2026-07-30/copilot-app-japanese.pptx) が提供されています。実演の準備に活用してください。
- 上流の [日本語 App ワークショップ](https://github-samples.github.io/copilot-workshops/ja-jp/app/) は参照用の資料です。本教材では、実機検証済みの操作手順と修正済み演習テンプレートを使用します。

### 公式イベント運営の厳格な条件
- **新規申請の受付終了**：指定コミットの時点で、公式 Dev Days の新規イベント申請は定員到達により受付・承認を終了しています。本コピー内の旧イベント申請案内ではなく、[公式 FAQ](https://github.com/github/dev-days/blob/main/FAQ.md) で最新状況を確認してください。
- **登録の一本化**：公式 Dev Days として承認済みのイベントは、Luma で Public に設定し、参加登録も Luma に集約します。他の告知サービスを併用する場合も、登録窓口を分散させてはなりません。日程変更なども Luma に反映します。
- **必須登録項目**：登録時には、国、GitHub ユーザー名、職種への回答を必須とします（会社名および連絡への同意は任意です）。
- **報告義務**：参加者には [終了後アンケート](https://gh.io/dev-days/feedback) を案内し、主催者は飲食費精算の有無にかかわらず [開催報告](https://gh.io/dev-days/event-report) を提出する義務があります。

> [!IMPORTANT]
> 上記は公式イベントとして承認された場合の運営条件です。独立した勉強会を開催しても、公式承認や特典が自動的に付与されるわけではありません。クーポン、物品、飲食精算はイベントごとの個別承認条件に従います。受講者全員への提供を安易に約束せず、公式 FAQ と承認時の案内を確認してください。また、イベントを Public にする条件と、演習コードの公開範囲（本教材では非公開推奨）は別問題です。

## 3. 運営時間配分案（180分枠）

以下の配分は本教材独自の運営案であり、実測所要時間ではありません。演習0および演習1の環境準備は、原則として事前準備で済ませておく前提です。原本シナリオの想定（60〜90分）に対し、App の操作支援やレビュー時間を手厚く確保しています。

| 時間配分 | 演習項目 | 内容と進行上の留意点 |
| :--- | :--- | :--- |
| **30分** | 導入セッション | Dev Days の App スライドなどを活用した概要説明 |
| **15分** | 演習0・1 | 環境・対象リポジトリの確認と初回接続 |
| **20分** | 演習2 | 星評価の実装、アクセシビリティ対応、PR 作成と通常マージ |
| **15分** | 演習3 | カスタム指示の更新、ドキュメント標準化、PR 作成と通常マージ |
| **10分** | （休憩） | — |
| **30分** | 演習4 | フィルター機能の計画承認、Autopilot 自律実装、品質検査 |
| **20分** | 演習5 | Playwright MCP の設定確認、再起動、ブラウザー検証 |
| **15分** | 演習6 | PR レビューと通常マージ／Agent Merge の実機デモ |
| **10分** | 演習7 | Canvas デモ、トリアージボードによる優先順位整理 |
| **10分** | 演習8 | 振り返りと手動 Automation の実機デモ |
| **5分** | 質疑・予備 | 質問対応と終了確認 |

**進行上の注意**：CI の待機時間や受講者の環境構築が長引いた場合は、無理に受講者全員の操作を継続させず、後半の演習を「講師デモ」に切り替えて進行してください。その際、受講者本人が実施していない項目は記録に残し、「全員が全演習を完了した」と案内してはなりません。Canvas や Automation を全員にハンズオンさせる場合は、別途追加枠を確保する必要があります。

## 4. 開催前のリハーサル項目

講師は開催前に、自身の非公開コピーを用いて次の項目を必ずリハーサルしてください。

1. **環境とバージョンの記録**：演習0〜8を順に通し、App および CLI のバージョン、Node.js バージョン、テンプレートのコミット SHA、OS を記録します。
2. **マージ結果の継承確認**：演習2および演習3のマージ結果が、演習4の開始時に正しく引き継がれていることを確認します（CLI コースのように publisher helper が事前に存在すると仮定しないでください）。
3. **現行 UI 経路の検証**：[UI 確認表](ui-check.md) に沿って、現行 App の操作経路と画面表示を突き合わせます。CLI の緊急対応は、本編とは別の「作業保全リハーサル」として別途確認します。
4. **利用権限とポリシーの切り分け**：App 用および CLI 用の利用ポリシー、残り利用枠（AI Credits など）、ネットワーク接続、必要な GitHub 権限を確認します。UI の変更と、認証や利用枠の枯渇による問題を混同しないようにしてください。
5. **テストケースとデータの確認**：星評価の null ケース、フィルターの複合条件・解除・該当なし表示を確認します。通常データ（seed）に存在しない条件は検証用データでテストし、実際の画面操作による結果と明確に区別します。
6. **MCP 実行環境の切り分け**：MCP 用の Chrome と E2E 用の Chromium を明確に区別します。MCP 接続失敗時はプロセス状態、App の MCP 設定、セッション再起動を確認してください。手動ブラウザー検証へ切り替えた場合は、MCP 体験を「未実施」とします。
7. **テンプレートの修正版確認**：教材用テンプレートの YAML および MCP 修正が適用済みであること（配布版 `v2026.09.13.1` と開始コミット）を確認します。演習済みの検証リポジトリを開始用として誤配布しないよう注意してください。
8. **依存性監査の未解決事項**：配布元 WORKSHOP.md の依存監査において、未解決事項（`drizzle-kit` 配下の Moderate 4件）と確認範囲を配布前に把握しておきます。機能テストの成功のみで安易に配布可能と判定してはなりません。
9. **終了時の後始末**：開発サーバー、演習用 Codespace、不要な定期実行を停止します（作成した PR や未保存の作業ツリーを誤って削除しないようにしてください）。

## 5. 当日の操作支援と緊急対応ルール

受講者が操作に詰まった場合は、次の原則に従って支援します。

1. **現状の正確な把握**：現在の章、操作の目的、現在の画面表示を確認し、[UI 確認表](ui-check.md) と照合して差分を記録します。画面上の位置だけで探さず、機能名、対象リポジトリ、セッションの状態を照合してください。
2. **推測による案内の禁止**：講師が実際に検証済みの現行操作経路のみを案内します。見つからない機能に対して、推測で操作を指示してはなりません。
3. **デモ・ペア操作への切り替え**：受講者環境で操作が再現できない場合は、同じ操作を講師の実機デモまたはペア操作で示します。受講者が画面を見ただけの項目は「デモ確認」と記録し、受講者本人の実施とは区別してください。
4. **CLI 緊急対応の限定的適用**：受講者の作業を保全し、実装を前へ進める必要がある場合に限り、[講師専用 CLI 手順](emergency-cli.md) を使用します。時間が経過したという理由だけで安易に CLI へ切り替えてはなりません。また、CLI で実装を完了させても、App の操作体験は「未完了」として記録します。

### 「機能体験」の厳格な判定基準
- 環境、権限、利用枠の問題は、UI の仕様変更とは明確に切り分けて記録します。
- 講師環境でも機能を確認できない章は延期とし、無理に実施可能と案内してはなりません。
- **代用と体験の峻別**：通常の PR 作成、通常の Markdown 文書、単発の要約プロンプト実行を、それぞれ Agent Merge、Canvas、Automation の「実施」に数えてはなりません。
